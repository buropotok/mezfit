# FitnessProgramer Base 2: анатомия и оборудование — этап подготовки

Этап 1 создаёт воспроизводимую очередь для 1 173 **уникальных** упражнений FitnessProgramer и диагностику незаполненных или несогласованных полей. Исходные карточки Base 2, уже опубликованные данные, GIF и интерфейс на данном этапе не меняются.

## Структура и гарантии

- **batches.json**: неизменяемый реестр 12 пачек (11 по 100 и последняя 73). Один ID формата fitnessprogramer:<slug> представлен одним исходным JSON. Каждая карточка содержит ожидаемый Git blob SHA, исходный путь, выбор одной основной UI-категории, набор альтернативных категорий и пути идентичных копий для аудита. Наличие в нескольких каталогах не создаёт второе упражнение.
- **inventory-report.json**: проверенные статистические показатели по дереву Git и честная отметка, что полная диагностика содержимого JSON пока не проводилась.
- **diagnose.mjs**: скрипт только для чтения исходных карточек, верификации Git SHA каждого JSON и проверки таксономии.
- **status.json**: существует и изменяется **только** в координационной ветке data/fitnessprogramer-enrichment-coordination. Все 12 пачек при создании свободны (new).

Файл batches.json в рабочей ветке подготовки и в координационной ветке должен быть побайтно одинаковым (Git blob SHA: b3b9a82f7ec8c008f3dab56a0ddcc6c3bb1679c4). Источник зафиксирован на коммите 043a7be1ddbfc669910bab86c33e11aa41b9a87b.

Из 1 673 JSON ровно 1 173 уникальных имени файла. Все 375 групп дубликатов имеют одинаковый blob SHA; 500 физических копий исключены из очереди. У 248 упражнений исходные категории дают разные категории в интерфейсе. Для них автоматический выбор категории помечен как **предварительный**, а category_review_required требует содержательной проверки при обработке пачки. Такую проверку нельзя считать уже выполненной. Приоритет B001 — имена со smith/machine; затем lever/cable. Это приоритет по названию, не по подтверждённой пустоте анатомии.

## Запуск диагностического скрипта

В локальном checkout репозитория с исходными файлами выполнить отдельную команду (не npm, не typecheck и не тесты):

    node tools/exercise-work/anatomy-enrichment/diagnose.mjs --output /tmp/mezfit-anatomy-diagnostics.json

Если реестр находится по другому пути, передать --manifest путь/к/batches.json. Без --output скрипт выводит только общую статистику и не создаёт файлы.

Диагностика:
- проверяет покрытие всех 1 173 уникальных ID и исходных 1 673 путей;
- подтверждает SHA каждого JSON и идентичность дополнительных копий;
- выявляет полностью пустую анатомию и отсутствие основных мышц;
- сравнивает существующие мышцы с **69 идентификаторами** из audit/visual/input/taxonomy.json, применяя существующие алиасы fitnessProgramerCatalogue.ts;
- сравнивает оборудование с EQUIPMENT_LABELS из src/data/exercises/publicExerciseFilters.ts, выявляет общий Machine, пустоту и неизвестные названия;
- выдаёт показатели и список проблем по каждому ID, не исправляя данные и не делая биомеханических выводов.

Пустые мышцы у кардио или упражнений на мобильность могут быть допустимы; такие случаи требуют содержательной проверки, а не автоматического добавления мышц. Если исходник или словарь расходится с зафиксированным контрактом, скрипт останавливается с ошибкой.

## Работа будущих агентов с пачками

Перед каждой задачей читать корневой AGENTS.md и docs/architecture/local-first-storage-sync.md. За один запуск обрабатывать не более 100 **уникальных** упражнений; не загружать весь каталог в модельный контекст.

1. Получить HEAD координационной ветки и status.json из **того же коммита**; выбрать первую свободную пачку.
2. Атомарно заявить право на неё через Git API: новое дерево, коммит с родителем = считанный HEAD, update_ref с expected_sha, без force; выставить agent, claim_id и lease_until (2 часа).
3. Перечитать статус; только после подтверждения claim_id работать в собственной ветке от актуального main. Продлевать аренду аналогично и проверять её перед публикацией результата.
4. Для пустой анатомии исследовать движение и источники; для непустой — сначала нормализовать ID и проверить соответствие таксономии, не переделывая корректные данные без причины. Разделять основные, вспомогательные и стабилизирующие мышцы.
5. Для отсутствующего или общего оборудования определить корректный существующий фильтр. Smith Machine, «Машина Смита» и «Тренажёр Смита» должны вести к каноническому ID smith machine и названию **«Тренажёр Смита»**. Не вводить параллельные фильтры; новые только после решения владельца.
6. Выбрать **одну** итоговую категорию. При category_review_required выполнить смысловую проверку, а не механически принять выбранный при подготовке вариант.
7. Сохранить уточнения **в отдельном версионированном JSON результата пачки** с источниками и уровнем уверенности. Помечать каждое упражнение verified, partial, needs_review или unchanged. Пачка completed означает, что все карточки рассмотрены и сохранены, а не то, что любой пробел был заполнен.
8. Проверить файлы, полноту, diff, регламент AGENTS.md, действующую аренду и реальный коммит. Только после этого атомарно выставить completed и сохранить result_branch, result_commit, completed_at, result_stats. При утрате аренды не публиковать и не изменять статус. Автоматически переходить к следующей пачке только через новое атомарное закрепление.

Не редактировать assets/work, assets/exercises, существующие переводы, опубликованный выпуск Dexie и GIF. Не запускать npm/typecheck/сборку/проектные тесты; они выполняются в CI после PR. Перед PR — ревью кода, релевантности имеющихся тестов и пунктов audit.

## За пределами этапа 1

Исследование и запись реальной анатомии/оборудования начнутся с B001. После проверки результатов отдельная задача внедрит их в приложение, обеспечив одну карточку в одной категории и единый набор фильтров Базы 1/Базы 2. Вопрос безопасного обновления опубликованного каталога решается отдельно, без изменения механизма загрузки медиа из Яндекса и R2.
