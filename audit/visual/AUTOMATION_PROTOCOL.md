# Mezfit visual audit — автоматический протокол (временный эксперимент)

**Scope:** только `audit/visual/**` репозитория `buropotok/mezfit`, ветка `main`. Изменения исходного каталога, исходников приложения и Dexie Cloud запрещены. Прямая запись **только файлов аудита** в `main` разрешена пользователем 2026-10-21 в качестве исключения из стандартного PR-workflow.

## Источники

- `audit_execution_plan.json` — единственный источник состояния и точных ID этапов;
- `input/catalogue_stage_NN.jsonl` — исходные полные метаданные ровно тех упражнений, которые перечислены в этапе (неизменённые записи `exercises[]` исходного JSON);
- `input/taxonomy.json` — таксономия исходного каталога, включая все 69 анатомических ID;
- `input/manifest.json` — контрольные SHA-256 этапных проекций и оригинального каталога;
- `input/audit_queue.json` и `input/NEW_CHAT_VISUAL_AUDIT_PROMPT.md` — исходный порядок и методика;
- `results/batch_NN.jsonl` и `results/audit_checkpoint_stage_NN.json` — результаты проверок;
- `results/issues_batch_NN.csv` — реестр проблем.

Первоисточник — архив `mezfit_visual_audit_handoff.zip`: каталог SHA-256 `5ce3e6b15117e115a1e10ac31573eb85eea6bf284a72971e5ca1ee02572aa40c`. Каталог разбит на этапные файлы без изменения полей записей, чтобы не передавать 5,6 МБ при каждом запуске. Полная `taxonomy` вынесена отдельно. Исходный полный JSON не редактируется.

## Однопоточный polling

1. Прочитать `AGENTS.md` и `docs/architecture/local-first-storage-sync.md`; выполнять операции GitHub только в названном каталоге.
2. Прочитать **свежий** `audit_execution_plan.json`, включая текущий blob SHA.
3. Если корневой `status` = `paused`, `blocked`, `in_progress` или `completed`: **не запускать этап**. При `in_progress` можно уведомить о подозрительно старом lock, но не перехватывать процесс автоматически.
4. Если `status=ready`, проверить предыдущий этап: он `completed`, `results_committed=true`, его файл результатов реально существует, в нём проверены именно соответствующие ID. Найти первый `pending`.
5. Атомарно перевести задачу и этап в `in_progress`, записать `current_stage` и уникальный `lock` с `started_at`, используя `fetch_file` + `update_file` с **исходным blob SHA**. Если запись не прошла из-за конкуренции/изменения SHA, немедленно прекратить работу без обработки GIF. После успешного захвата заново прочитать файл и убедиться, что lock принадлежит этому запуску.
6. Анализировать только список `exercise_ids` выбранного этапа. По каждому упражнению скачать настоящий GIF из `hasaneyldrm/exercises-dataset` и визуально проверить **несколько фаз**; проверить name_ru, name_en, инструкции RU/EN, оборудование, категорию, движение и анатомию. Нельзя переносить старые аннотации как готовые выводы. **Строгий максимум 100 впервые просмотренных GIF за один запуск/этап.** В последнем этапе 24. При недоступном GIF — `blocked`, не засчитывать как просмотренный.
7. Каждый вывод — отдельная JSONL-запись; **обязательное поле `name_ru` — текущее, дословно из исходного каталога**, аналогично `name_en`. Для каждого GIF указывать frame_count, reviewed_frames, наблюдаемое движение, поля и статус, уверенность, причины правок. Для находок сохранять проверяемые кадры/описания и ссылки на исходный GIF. Не выдумывать якобы просмотренные кадры.
8. Писать `results/batch_NN.jsonl`, `results/issues_batch_NN.csv`, `results/audit_checkpoint_stage_NN.json` **до** изменения статуса этапа. Отчёт в чате: этап и накопленный прогресс, счетчики статусов и 10 основных находок с текущими русскими названиями. Предоставить ссылки GitHub на каждый файл.
9. Машинно удостовериться в количестве уникальных ID, отсутствии пересечений с уже завершёнными этапами, точном составе выбранного списка, правильности `gif_url` и том, что результаты действительно записаны и доступны через GitHub. Если имеются блокировки/неполные результаты, сохранить промежуточное состояние и выставить корневой `blocked` (не выдавать `completed`).
10. **Только после успешной проверки** обновить `audit_execution_plan.json` через свежий SHA: текущему этапу `status=completed`, `results_committed=true`; обновить `completed_exercises`, очистить `lock` и `current_stage`, назначить `next_stage` и корневой `status=ready`. Для финального этапа установить корневой `status=completed`.
11. Немедленно завершить данный запуск после **одного** этапа. Следующий этап вправе запускать **только следующий polling**, а не этот запуск.

## Изменение первоначального промпта

Требование `NEW_CHAT_VISUAL_AUDIT_PROMPT.md` «Жду команды „Продолжай“» заменяется **только для запланированных запусков** следующим правилом: разрешение на следующий этап даёт успешно записанный `status=ready` и успешно захваченный lock в управляющем JSON. Лимит 100 GIF за этап и все требования к фактической визуальной верификации сохраняются.

## Ограничения эксперимента

Обычная задача ChatGPT может не получить доступ к GitHub в контексте запланированного запуска, к операциям записи или к ресурсам, нужным для 100 GIF. Не утверждать успех без проверяемых коммитов; при невозможности чтения/записи оставить `paused` либо установить `blocked` только если удалось безопасно обновить план. Не создавать PR, workflow, второго агента или новый чат. Данные сохраняются на GitHub; локальные вложения прежнего чата не считаются доступными.
