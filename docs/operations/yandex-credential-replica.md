# Приватная credential-реплика Mezfit в Yandex

Этап 2 разделён на два PR. Первый подготавливает изолированный приёмник и
схему. Второй подключает точный POST-маршрут в действующем Gateway, D1 outbox
и отправителя. Оба этапа предшествуют парольному входу. GitHub Actions
проверяет транзакции на временной YDB с вымышленными данными.

## Деплой приёмника

1. После зелёного CI и merge в `main` открой [Deploy Mezfit credential replica](https://github.com/buropotok/mezfit/actions/workflows/deploy-mezfit-credential-replica.yml).
   Запусти от владельца репозитория на `main` с `mode=preview`. В логе будут
   только имена управляемых ресурсов и сведения о том, существуют ли они.
2. Один раз создай **новый независимый** GitHub Actions secret
   `MEZFIT_CREDENTIAL_REPLICATION_SECRET`. Из авторизованного Codespace:

   ```bash
   set -o pipefail
   python3 -c 'import secrets; print(secrets.token_urlsafe(32))' |
     gh secret set MEZFIT_CREDENTIAL_REPLICATION_SECRET --repo buropotok/mezfit
   ```

   Используются существующие `YC_FOLDER_ID` и `YC_DEPLOY_SA_ID` и
   федерация GitHub OIDC. Права деплоя должны позволять создать выделенные
   serverless YDB, Lockbox, приватную Cloud Function и runtime service
   account, назначить привязки на точно этих ресурсах и создать таблицы.
3. В том же workflow выбери ветку `main` и `mode=apply`. Ожидаемый результат:
   `Credential replica ready: schema verified, Lockbox pinned, anonymous invocation denied.`
   GitHub Actions не применяет этот контур автоматически после merge.

Приёмник `mezfit-credential-replica` использует выделенный runtime
`mezfit-credential-replica-runtime`. Прямые гранты — `ydb.editor` на
выделенной базе и `lockbox.payloadViewer` на выделенном секрете.
`functions.functionInvoker` на новой функции выдаётся существующему
OIDC-деплоеру для проверки. Роль `ydb.editor` применяется к базе целиком,
поэтому база отдельная от `account_replica`. Она serverless с лимитом 1 ГиБ
и защитой от удаления. Отдельная база создаёт дополнительный ресурс и
учитывает операции и хранение по тарифу serverless. До начала доставки
проверить унаследованные права облака и папки. Прямой readback
привязок не подтверждает отсутствие широких унаследованных ролей. Никто
из обычных приложений и старых runtime не получает новых прямых грантов.

Apply проверяет схему, точные прямые привязки и приватность функции.
Публикуется проверенная версия с тегом `credential`. Lockbox-версия
передаётся функции по ID версии. Повторный Apply не читает payload и
не меняет секрет. Замена GitHub Secret после создания Lockbox сама по себе
не меняет приёмник. Ротацию согласовать перед подключением отправителя,
с обслуживаемой паузой и обновлением pin у функции и настройки Worker.
При неудачном деплое эту стадию можно остановить, оставив защищённую базу
и прежний тег. До подключения отправителя функциональность приложения
от них не зависит. При будущей доставке откат версии функции должен
сохранять YDB-ревизии и tombstone. Удаление базы или сброс ревизий
требует отдельного решения.

## Контракт приёма

Внутренний POST требует отдельный bearer secret. Lambda-ответ содержит
только статус, ревизию или безопасный код. `user_id`, `app_user_id` и
`telegram_id` передаются каноническими десятичными строками. YDB хранит
их как `Uint64`, а Python сравнивает целые непосредственно. Предел для
Telegram — `2^52−1`, для внутренних ID и ревизий — `2^53−1`.
Для legacy Telegram ID сверяется с `user_id`. При большем `user_id`
подтверждённая Telegram-привязка может отсутствовать. Логин хранится
в нормализованном виде из D1. `pass_hash` принимает `NULL` или строку
Argon2id PHC. Этот формат не определяет параметры хеширования или
политику входа. Функция не вычисляет хеши и не пишет тело, логин, ID и
хеш в логи. Парольные данные не расширяют `account_replica` и `MeResponse`.

Снимок и два lookup-ключа на логин и реальный Telegram ID обновляются
одной serializable-транзакцией. Первичный ключ каждой lookup-таблицы
соответствует ровно одному владельцу. При конфликте новый снимок
не применяется. Старый ключ освобождается только при применении
новой ревизии. Следующий отправитель должен повторять отказ при переносе
логина между ID, пока не доставлена ревизия, освобождающая ключ.
Одинаковые данные той же ревизии возвращают `duplicate`; другой снимок той
же ревизии возвращает `REVISION_CONFLICT`. Старая ревизия возвращает
`stale`. Для ACK отправитель должен отдельно проверять точное совпадение
ревизии. `disabled` и отзыв пароля исключают старый verifier, а `deleted`
оставляет terminal tombstone без привязки, логина и хеша. Более высокая
ревизия не активирует удалённый ID повторно. Пока доставка не подтверждена
и нет модели свежести и отзыва, политика входа для этой реплики отсутствует.

## Подключение доставки в следующем PR

1. Общий Gateway `mezfit-web` должен получить один точный POST с
   проверкой сохранности остальных маршрутов. Защита и новая привязка
   для Gateway проверяются до активации отправителя. Проверять отказ
   без секрета и HTTPS с запретом redirect, используя фиксированный URL.
2. В D1 использовать read-only [preview существующих соответствий](../../tools/cloudflare/password-credentials/preview.sql),
   затем отдельно согласовать [заполнение](../../tools/cloudflare/password-credentials/backfill.sql)
   при отсутствии соответствий. Deploy приёмника эти SQL не выполняет.
3. Новая постановка существующих credentials в D1 outbox должна работать
   отдельно и идемпотентно. После предварительного просмотра агрегатов
   выполнить только согласованную постановку, проверить доставку и YDB
   readback по агрегатам и ревизиям без секретов. Отсутствующая запись D1
   означает, что реплика аккаунта ещё не подготовлена.
4. После проверки доставки отдельный этап реализует серверную проверку
   пароля, отзыв, свежесть сессий и правила ролей для аккаунта без Telegram.
   Подключение сопоставления к Dexie и адаптация потребителей Telegram ID
   проходят после проверки ACL. Роль не выводится из наличия credential.
