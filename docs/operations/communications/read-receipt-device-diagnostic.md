# COMM-06: подтверждение прочтения на реальных устройствах

Локальный сброс unread не доказывает доставку `discussionReadStates` другому
участнику. Ответное сообщение тоже не заменяет authored read-state.
При сохранении одной галочки после полного перезапуска отправителя нужно
сравнить локальные данные двух аккаунтов, прежде чем менять запись или ACL.

## Получение отчёта

1. Получатель открывает переписку и просматривает входящее сообщение.
2. На каждом устройстве открыть внутри Telegram существующую
   [диагностику Dexie Cloud](https://t.me/mezfit_bot?startapp=cloud_auth_check).
3. Нажать «Проверить синхронизацию», дождаться обычного завершения синхронизации.
4. В разделе «Отметки прочтения» нажать «Скопировать отчёт о прочтении».
   Передать два отчёта с подписями «отправитель» и «получатель» и текущим
   статусом синхронизации. Если буфер недоступен, достаточно снимка раздела.

Отчёт агрегирован по локально доступным обсуждениям данного аккаунта, а не по
одному чату. Он не содержит ID, имён, заголовков, текста, времени сообщений,
токенов или полного текста ошибок. Он показывает только конфигурацию и числа.
Чтение выполняется одной read-only Dexie-транзакцией; liveQuery обновляет
снимок при репликации. Экран использует уже существующий Addon pull и не пишет
сообщения/отметки, не запускает отдельный транспорт и не меняет ACL/схему.

## Интерпретация

- `incomingReadLocally`/`acceptedOwnStates` у получателя показывают локальную
  границу просмотра. Эти числа не доказывают публикацию на сервере.
- `peerStates` у отправителя показывает наличие чужих отметок в его IndexedDB.
  Отсутствие при успешном локальном просмотре у получателя требует проверки
  репликации/доступа, а не замены галочек статусом sync.
- `rejected` разделяет причины: идентичность, владелец, ветка/realm,
  отсутствие/формат курсора, несовпадение курсора с `lastReadMessageId`.
  Для каждой записи считается первая причина; отсутствующий курсор может быть
  пустой начальной или исторической отметкой.
- `outgoingWithPeerState` отличается от `outgoingRead`: корректный чужой курсор
  может предшествовать сообщению. Границы сопоставляются только внутри исходной
  ветки и realm, включая сохранённые legacy-ветки канонического обсуждения.
- `outgoingRead > 0` при одной галочке ещё не доказывает UI-дефект именно для
  конкретного сообщения: отчёт агрегирован. Далее нужно сузить наблюдение до
  нужного обсуждения, сохраняя приватность данных.

## Найденная причина и совместимость (2026-11-07)

Отчёт с `peerStates: 4`, `acceptedPeerStates: 0`, `rejected.identity: 4`
показал, что чужие отметки уже пришли, но их ID не совпадают с ожидаемой строкой.
Это не отсутствие репликации. В исходниках опубликованного `dexie-cloud-addon`
4.4.15 (source map `dist/modern/dexie-cloud-addon.min.js.map`,
`src/sync/applyServerChanges.ts`) `keyDecoder` декодирует ключи вида `[...]`
через JSON.parse и затем устанавливает результат в inline primary key.
Старый ID приложения как раз являлся JSON-строкой массива.

Исправление вводит префикс `discussion-read:` для новых записей и строгое
чтение исторических строковых/декодированных ключей. Диагностика использует ту же
проверку ID. Никакое чтение не выводится из факта ответа или общего sync-status.
После deploy уже доставленные корректные старые отметки должны приниматься без
повторной отправки сообщений. Проверить две галочки и приложить новые отчёты в
обоих направлениях, включая повторное открытие и offline/reconnect.

Межаккаунтная репликация, два устройства и offline/reconnect требуют фактической
проверки; локальные тесты с формой декодированного ключа её не заменяют.
Активация функций приложения после
merge/deploy обычная: новые flags, env, workflows или настройка не нужны.
