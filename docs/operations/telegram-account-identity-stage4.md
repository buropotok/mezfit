# Разделение идентификаторов Telegram и Mezfit

В Dexie Cloud идентификатор пользователя имеет вид `tg:<user_id>`. Для
вызовов Bot API Cloudflare использует подтверждённую связь
`password_credentials.user_id → app_user.id → app_user.telegram_user_id`.
После проверки данных Mini App или webhook направление обратное. Клиентские
параметры адресуют записи, а право доступа устанавливает сервер.

| Владелец | Путь и право доступа | Проверка |
| --- | --- | --- |
| Уведомления и напоминания Cloudflare | Realm, автор и предпочтения проверяются по Dexie ID. D1 связывает получателя с чатом, а личное напоминание сверяет роль по `app_user.id`. | Отдельные ID для linked, отсутствие доставки для unlinked, повтор при отказе D1, прежняя идемпотентность. |
| Приглашения и тестовый сброс | Бот оперирует проверенным Telegram ID, membership — внутренними ID. Для сброса нужны разрешённый тренер, активная пара D1 и проверенный realm. | Совпадение прежних realm и проверка роли, пары и участников. |
| Профили и аватары | Получение фото по проверенной сессии Telegram, запись по постоянному ID и проверенному relationship realm. UI читает действующие Dexie Cloud Blob/Flex. | Источник фото и владелец записи различаются, ошибка Telegram сохраняет ранее опубликованное фото. |
| Cloudflare R2 и подтверждение расписания | После проверки initData D1 подтверждает внутреннего actor. R2 проверяет прежний контракт sender prefix или точный опубликованный объект и членство. | Прежние ключи для Telegram-first, отказ при отсутствии связи и запрет доступа к чужим объектам. |
| Назначение программ и анкеты контактов | В программе используется внутренний идентификатор участника. Анкета не получает внешний ID из membership и не показывает его. | Тот же realm и план, отсутствие ложного поля Telegram ID. |
| Yandex Browser Auth | Сохраняет проверку активной записи в `account_replica` и ограничение Telegram-first. | CI, Apply и браузерный вход с VPN на PR #933. |
| Yandex media и локальные базы | Подписант Yandex media и bootstrap Mini App пока предполагают Telegram-first. Ключи локальных баз существующих аккаунтов сохраняются. | До активации новых субъектов подписант должен получить подтверждённый внутренний ID из существующей реплики, а bootstrap и очистка должны использовать стабильный ключ аккаунта. |

Перед публикацией Worker необходимо проверить полноту соответствий для уже
существующих Telegram-аккаунтов средствами [этапа 3](dexie-account-identity-stage3.md#перед-включением-и-при-откате).
Без соответствия операции, требующие подтверждённого Telegram-доступа,
завершаются контролируемой ошибкой или пропускают отправку. При регистрации
через действующий Telegram bootstrap соответствие создаётся по уже проверенному
ID и существующему ключу строки. Запись и очередь репликации используют
существующую D1-схему.

До следующего этапа оба пути выдачи токенов допускают только Telegram-first.
Привязка Telegram и выдача субъектов из зарезервированного диапазона остаются
отдельным развёртыванием. Для Yandex media нужен согласованный контракт чтения
существующей реплики с прежним хешем у Telegram-first. Для Mini App нужно
передавать подтверждённый устойчивый ID в bootstrap и выбор локальной базы,
сохранив имена баз старых аккаунтов. Прежнюю Worker-версию можно вернуть
штатным деплоем до появления реальных linked password-first аккаунтов.
