# Постоянный ID при выдаче Dexie-токена

Этап 3 подготавливает оба пути. После merge штатный деплой реплики
даёт существующей браузерной функции чтение YDB и включает lookup для
браузерных маршрутов после проверки готовности. Параметр Worker
`MEZFIT_DEXIE_D1_MAPPING_ENABLED` остаётся выключенным в этом срезе.

| Путь | Подтверждение | Текущий источник | Целевой источник | Субъект для Telegram-first |
| --- | --- | --- | --- | --- |
| Mini App | Подписанный Telegram initData | Telegram ID из подписанного initData | D1, `app_user.telegram_user_id → password_credentials.user_id` | `tg:<user_id>` с тем же значением, что раньше |
| Браузер | Telegram OIDC или подтверждённый bot login_url и серверная cookie | Telegram ID из проверенной cookie | Read-only lookup по `account_replica.external_telegram_id` в YDB | `tg:<user_id>` с тем же значением, что раньше |

Оба пути передают субъект в Dexie Cloud, сохраняя `ACCESS_DB` и привязку
к ключу устройства. На этом этапе у существующих пользователей значение
совпадает с прежним. Программы, тренировки, сообщения, участники realms,
владельцы, имена локальных баз и Telegram-интеграции продолжают использовать
существующие контракты. Браузер принимает cookie v1/v2 и продолжает выпускать v2. Проверка host
и origin и продление без нового OIDC сохраняются.

## Mini App

При включённом серверном флаге Worker выполняет lookup после проверки
initData и ключа устройства. Если учётная запись уже существует в
`app_user`, допускается идемпотентное создание отсутствующего соответствия
через `passwordCredentials`. Вставка и постановка репликации проходят
в одной D1-транзакции. Первый `app_user` по-прежнему создаёт действующий
bootstrap, например при `GET /api/me`. Обмен токена создаёт только
соответствие существующей строки. История полных снимков в outbox
не даёт токен-эндпоинту заново создать ранее удалённое соответствие.
Эта проверка выполняется в том же SQL-выражении, что и вставка.

Отсутствующий аккаунт, отказ D1, конфликт или reserved ID дают один
`503 DEXIE_CLOUD_UNAVAILABLE` до запроса в Dexie. Лог содержит только
фиксированный код. Включённый путь не продолжает обмен с Telegram ID
после ошибки. D1 остаётся источником истины для Mini App, поэтому этот
путь не зависит от доступности YDB и получения ACK от Яндекса.

## Браузер

Cloud Function получает токен своего сервисного аккаунта из контекста
вызова. Включённый путь читает существующую serverless YDB по
`MEZFIT_BROWSER_ACCOUNT_YDB_PATH`. Параметризованный запрос использует
синхронный дополнительный индекс `account_external_telegram_idx` и
читает максимум две записи. Индекс добавляет штатный деплой реплики.
Из YDB выбираются ключ строки, внешний Telegram ID, состояние, ревизия и
JSON профиля для сверки. Логин и хеш не выбираются.

Lookup выполняется до выпуска или продления cookie и независимо перед
каждой выдачей Dexie-токена. Допускается ровно одна активная строка,
в которой подтверждённые Telegram ID и постоянный user_id совпадают.
Субъект из резервного диапазона отклоняется. Ошибка чтения, отсутствие
данных, повреждённое соответствие и некорректная ревизия дают
503 без очистки существующей cookie и без запроса в Dexie. Успешное
обновление cookie v1/v2 не требует повторного обращения к Telegram.

### Деплой и отставание реплики

В MVP изменения в D1 вступают в силу для браузера после доставки в YDB.
Браузерная функция использует состояние прочитанного снимка и не обращается
к D1 для проверки каждого входа.

[Штатный Deploy Mezfit account replica](https://github.com/buropotok/mezfit/actions/workflows/deploy-mezfit-account-replica.yml)
назначает `ydb.viewer` существующему `mezfit-browser-auth-runtime` только
на базе реплики. После проверки схемы, индекса и покрытия существующих
реплицированных Telegram-аккаунтов он публикует новые версии действующей
Cloud Function. Деплой включает YDB lookup на обслуживающих тегах,
используя текущие Lockbox-привязки и Gateway.

Проверка готовности выводит только число подготовленных снимков. Если
покрытие неполное, завершить существующий backfill и повторить деплой.
Привязки тегов изменяются только после публикации и сверки всех новых
версий. Идентификаторы предыдущих версий выводятся в лог для отката.
Формат cookie позволяет переключать теги без завершения сессий.

## Перед включением и при откате

1. Проверить успешный `Deploy Mezfit account replica`. После #932 этот
   workflow проверяет ответ 401 на рабочем адресе шлюза. Этот результат
   подтверждает готовность маршрута и проверку схемы, но не полноту данных.
2. Сверить агрегаты D1 и YDB для реально существующих Telegram-first
   аккаунтов. Считать отсутствующие соответствия, частичные или
   неподтверждённые снимки и конфликтующие привязки. Пользоваться
   [порядком проверки и заполнения реплики](yandex-account-replica.md#общий-снимок-профиля-и-учётных-данных).
   Сверку UID и ревизий делать в закрытом контуре и выводить только итоги.
   Не запускать backfill или тестовую запись при read-only проверке.
3. После деплоя браузера проверить старые cookie, свежий OIDC,
   login_url и Mini App с существующим аккаунтом. На реальных устройствах
   проверить оба способа входа и обновление токена с VPN и без VPN.
   Подтвердить прежний субъект и доступ к личным и общим realms. Для
   аккаунта без соответствия проверять отказ без выдачи токена.
4. Откат Mini App до включения парольных аккаунтов — выключить серверный
   флаг и повторно развернуть Worker. Это допустимо, только пока живых
   парольных привязок и выданных субъектов из резервного диапазона нет.
   После появления таких аккаунтов возврат к Telegram-формуле недопустим.
