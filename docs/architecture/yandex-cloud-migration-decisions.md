### 1.1 Канонические границы данных

Существующая бизнес-архитектура **не заменяется** миграцией веб-хостинга:

```text
React Coach / Client UI
        ↓
typed domain repositories / application services
        ↓
Dexie.js / IndexedDB (local working subset)
        ↕
Dexie Cloud Addon
        ↕
Dexie Cloud (единственная authoritative бизнес-БД, realm ACL)
```

Привилегированные действия (проверка Telegram identity, выдача Dexie Cloud токенов, приглашения/членство, контроль доступа, отдельные API/медиа-операции) **обязательно** остаются серверными. Сейчас их значительная часть находится в Cloudflare Worker; переносить необходимые для повседневной работы операции на Yandex следует по отдельным контрактным срезам с сохранением всех бизнес-проверок. Регистрация, приглашения, provisioning relationship membership и Telegram Bot API остаются на CF согласно YC-13–YC-16. Cloudflare D1/R2/Workers, связанные с legacy API, медиа и техническими миграционными задачами, не объявлены автоматически удалёнными.

Существующая интеграция некоторых медиа с **Yandex Object Storage/Cloud Functions** (включая коммуникационные медиа и FitnessProgramer Base 2) — **отдельный уже существующий подсистемный контур**, а не доказательство завершённого переноса основного backend. Его контракты, fallback и ограничения описаны в [local-first-storage-sync.md](local-first-storage-sync.md) и профильных документах коммуникаций. Новый SPA-бакет с ними не смешивать.

### 1.2 Идентификация: решение владельца от 2026-11-24

Целевой аудит обнаружил зависимость от текущего ID в токенах Dexie Cloud, ACL, relationship realms, профилях, уведомлениях, media signer и локальных базах/кешах. Масштабная смена семантики ID ради одного дополнительного способа входа несоразмерна риску регрессий. Основной сценарий привлечения клиентов — приглашение тренером через Telegram. VPN при первоначальном входе допустим; повторный вход возможен при истечении/отзыве сессии, смене устройства или очистке данных.

- Для старых и новых пользователей MVP сохранять `tg:<реальный Telegram ID>` как внутренний `userId`. Mini App и браузерный OIDC должны приводить к одной и той же подтверждённой идентичности. Не доверять ID, переданному клиентом.
- Не реализовывать унификацию под несколько провайдеров, `mz:<uuid>`, синтетический числовой диапазон `tg:`, сопоставление VK ID или отдельный реестр identity в текущем roadmap. Обсуждавшийся числовой диапазон остаётся только отложенным вариантом, не контрактом.
- Приоритет после OIDC — защищённая серверная сессия, восстановление после перезапуска, продление без Telegram, Dexie Cloud token exchange/refresh с неизменным `sub`, перенос необходимых API в Yandex. Не ослаблять серверные ACL. Конкретная политика TTL/refresh/revocation требует отдельного проектирования.
- Проверить работу web/Capacitor на реальных устройствах без VPN после входа; отдельно подтвердить доступность Dexie Cloud, медиа и других обязательных зависимостей. Telegram Bot API, уведомления и обновление Telegram-профилей остаются интеграциями, но их недоступность не должна блокировать основной сценарий.
- Вернуться к провайдер-независимой identity только при подтверждённой существенной бизнес-потребности и новом решении владельца. Перед этим повторить [аудит зависимостей Telegram ID](../../audit/2026-11-24_telegram_identity_dependency_audit.md) на актуальном main, согласовать план сохранения ID/ACL, совместимость и откат.

### 1.3 Регистрация и репликация учётных записей: решение владельца от 2026-11-25

**Статус:** утверждённая целевая архитектура, не реализация. Пользователь подтвердил успешную выдачу Dexie Cloud токена на Yandex (HTTP 200, subject совпадает) 2026-11-25; работающие OIDC, browser session, Token API и идентификаторы не входят в scope следующих PR при отсутствии конкретного дефекта. Индивидуальный серверный отзыв stateless-сессий не реализован; текущие ограничения описаны в [операционной документации browser auth](../operations/yandex-browser-telegram-login.md).

#### Границы ответственности

- CF D1 — источник учётной записи `app_user` и глобального набора `user_role` (coach, client, обе роли; до выбора роли возможен пустой набор). Сохранить существующие CF-потребители, включая приглашения и напоминания.
- YDB — серверная реплика полного действующего `MeResponse` (`user.id`, `telegramUserId`, `username`, `firstName`, `lastName`, `languageCode`, `photoUrl`, `isPremium`, `roles`) и технической версии репликации. Числовой D1 ID сохраняется как legacy-контракт, а не становится Dexie identity. Ключ аккаунта привязан к реальному Telegram ID, неизменный cloud subject — `tg:<telegramUserId>`.
- Глобальная роль приложения не равна роли в конкретном relationship realm. Не выводить набор глобальных ролей из `members.roles`, не хранить их как обычные редактируемые flex-атрибуты и не использовать реплику ролей для выдачи или подмены Dexie membership. Dexie Cloud остаётся authoritative для бизнес-профилей, связей, данных и realm ACL.
- Telegram Bot API, приглашения и уведомления остаются в CF. Приложение не зависит от доступности CF для обычной работы после первичного входа и готовности реплики. Механизм создания приглашений тренером из приложения без VPN нужно отдельно определить до включения соответствующего браузерного сценария; доступность CF из Yandex не предполагается.

#### Надёжная доставка

```text
CF: регистрация / выбор роли / принятие приглашения
  → D1: изменение учётных данных + запись outbox (атомарно)
  → доставка последнего полного состояния аккаунта
  → Yandex API Gateway → приватная Cloud Function → YDB
  → подтверждение только после устойчивой записи в YDB
  → CF: завершение задания именно доставленной версии
```

- Одна актуальная запись outbox на пользователя (`user_sync_outbox` — рабочее название), а не журнал всех промежуточных состояний. Записывать задание в одной атомарной D1-операции/транзакции с изменением учётных данных (например, `batch()`). Реплицировать при регистрации, выборе роли, принятии приглашения и при изменении учётных данных, если такое изменение предусмотрено. Не добавлять пересылку на каждый обычный запуск.
- При первой возможности попытаться доставить запись сразу; при сбое сохранять её в D1. Существующий Cron `*/5 * * * *` обрабатывает готовые к повтору задания. Ориентир задержек: 5, 10, 20, 40, затем 60 минут с ограничением на 60 минут. Сбой, таймаут, потерянный ответ или рестарт не удаляют задание. Сохранять число попыток, следующее время попытки и безопасный код ошибки; не логировать персональные данные и секреты. Не прекращать повторные попытки только из-за истечения срока хранения сообщения. Доставка гарантируется при восстановлении доступности и исправной инфраструктуре, а не при постоянном отказе.
- Версия аккаунта монотонна и сохраняется между доставками (в частности, не обнуляется после удаления/завершения задания). Отправлять согласованный snapshot роли и пользователя с его версией. YDB атомарно применяет только более новую версию; одинаковая версия того же snapshot идемпотентна, более старая не перезаписывает новую. Подтверждение конкретной версии не может удалить более новое задание, появившееся во время запроса. Точная схема, порядок транзакций и контракты ответа определяются в соответствующих PR.
- Принимающий endpoint аутентифицирует CF как серверного отправителя, проверяет формат и ограничения данных; не принимает произвольный пользовательский JSON, роль или ID как доверенный источник. Секреты server-to-server — только в серверном secret storage, права runtime — минимальные; не передавать их во frontend. Публичный Gateway route не означает публичную запись в YDB.
- Исключение из YC-08 для первого этапа: проверенный merge в `main` запускает `Deploy Mezfit account replica` с автоматическим Apply. Workflow ограничен YDB реплики, выделенными IAM/Lockbox и приватной функцией, а также одним маршрутом существующего Gateway. Внутренние проверки и readback обязательны. Ручной запуск, Preview и код не требуются. Использовать существующий Gateway с точным новым маршрутом, не ослабляя default JSON 503 и не изменяя работающие auth/Token API. До включения CF-отправителя проверить приём, повтор, устаревшую версию, отказ при неверной аутентификации и ошибки записи. Отдельно подтвердить доставку CF → Yandex на реальных ресурсах.
- До включения браузерного `/api/me` обеспечить реплики для тех существующих аккаунтов D1, которые должны продолжать работать. Способ первоначального заполнения (ограниченная идемпотентная постановка задач для нужных аккаунтов) согласовать при rollout; это не перенос legacy бизнес-данных.

#### Регистрация клиента в боте

1. Тренер делится ссылкой `https://t.me/<bot>?start=invite_<token>`. Бот получает проверенное Telegram-событие и показывает «Вы получили приглашение от тренера Иванова Ивана» (имя реального тренера из проверенного приглашения), кнопки «Принять» и «Отмена».
2. На «Принять» CF проверяет действительность токена, срок, отзыв, личность получателя и запрет self-link. Webhook Telegram проверяется сервером; callback привязан к получателю и конкретному приглашению. Не доверять подставленным клиентом ID. Повторный webhook/callback не создаёт дубликаты. «Отмена» не принимает приглашение и не аннулирует многоразовую ссылку тренера.
3. Переиспользовать provisioning и readback существующих Dexie Cloud realm/memberships согласно [dexie-cloud-invitations.md](dexie-cloud-invitations.md); сохранить существующую последовательность проверки и явного согласия. D1-аккаунт, роль client, legacy-проекция и outbox фиксируются по существующей семантике с атомарной постановкой задания. Не считать частично завершённый процесс успешным. При сбое возможен безопасный повтор.
4. После готовности регистрации и реплики бот подтверждает принятие и предлагает открыть `mezfit.online`. После отдельной проверки маршрута и домена кнопка использует `login_url`. Этот вход подтверждает тот же Telegram ID и создаёт существующую браузерную сессию без записи аккаунта, роли или связи. При задержке репликации не утверждать, что приложение полностью готово. Бот уже активирован взаимодействием с клиентом; дополнительный `BotStartScreen` в новом сценарии не нужен. Существующее приглашение Mini App остаётся рабочим до проверки нового сценария; удаление старого пути — отдельный согласованный этап.

#### Первичная регистрация тренера из браузера

- Существующий OIDC подтверждает личность в Yandex. Во время первоначального входа с VPN frontend передаёт в CF краткоживущее, проверяемое CF подтверждение личности от сервера Yandex. Не передавать cookie сессии Mezfit, ключ подписи или Dexie service credentials в CF через frontend; не строить фиктивный Telegram `initData`.
- CF идемпотентно разрешает/создаёт тот же аккаунт по реальному Telegram ID; глобальную роль сохраняет через существующую семантику явного выбора, не выдаёт relationship ACL по факту входа. CF формирует outbox, YDB получает подтверждённый snapshot. Протокол подтверждения, защита от подмены/replay, CORS и поведение при сбое на первом входе проектируются в PR этой регистрации, а не меняют рабочий OIDC заранее.
- Регистрационный обмен с CF нужен при первоначальной регистрации или согласованном изменении учётных данных, не для каждого открытия приложения. Если регистрация/доставка не завершена, это отдельное состояние, не подставлять вымышленный ID/роль.
- Впоследствии `GET /api/me` на Yandex читает только собственную реплику, используя подтверждённую cookie identity и прежний контракт `MeResponse`. Отсутствующая реплика и недоступная YDB — различные ошибки; не создавать независимый аккаунт в YDB, не проксировать скрытно в CF.

### 1.4 Постоянный user_id: решение владельца от 2026-11-27

Cloudflare D1 хранит постоянный внутренний `user_id` в `password_credentials`. `app_user_id` ссылается на прежний первичный ключ `app_user.id`. Реальный `telegram_id` хранится в `app_user.telegram_user_id`. Сервер ищет подтверждённый Telegram ID в `app_user` и по ключу строки получает запись `password_credentials`. В Telegram API передаётся только реальный, подтверждённый ID. Для аккаунта без Telegram ссылка `app_user_id` равна `NULL`, а логин и хеш обязательны.

- Существующие Telegram-аккаунты и будущие аккаунты, впервые созданные через Telegram, получают `user_id = telegram_id`. У существующих пользователей Dexie субъект сохраняет то же значение побитно. Алгоритм relationship realm, membership, ownership и ключи IndexedDB сохраняются.
- При будущей регистрации по паролю выделяется случайный `user_id` из диапазона `[4 503 599 627 370 496, 9 007 199 254 740 991]`, то есть `[2^52, Number.MAX_SAFE_INTEGER]`. Согласно [Telegram Mini Apps](https://core.telegram.org/bots/webapps#webappuser) и [Bot API](https://core.telegram.org/bots/api#user), ID пользователя имеет максимум 52 значащих бита. Текущие серверные проверки и хеш relationship realm поддерживают безопасные целые и их каноническое десятичное представление. Перед активацией повторно сверить контракт Telegram, все серверные источники проверенного ID, потребителей и результат preview D1. Если Telegram расширит предел, остановить выдачу новых соответствий вне поддерживаемого диапазона и согласовать переход. Существующие ID сохраняются.
- Worker-генератор использует 52 случайных бита Web Crypto. Будущий серверный вызывающий код передаёт атомарную вставку с `ON CONFLICT (user_id) DO NOTHING` и учитывает, была ли создана строка. Повторяется только коллизия первичного ключа, максимум восемь попыток. Конфликт логина или другая ошибка записи возвращается вызывающему коду. В D1 хранится SQL `INTEGER` со строгой проверкой диапазона и класса хранения. Объявление `ANY` в `STRICT`-таблице исключает неявное преобразование числового текста и дробей при записи.
- Этап 1 импортирует логин из локального Telegram username только при наличии корректного значения и отсутствии конфликта. Правило нормализации для этого этапа — строчные ASCII-буквы, цифры и знак подчёркивания, от 1 до 32 символов, без пробелов и Unicode. При конфликте регистра, дубликате в `app_user` или уже занятом логине оставляется `NULL`. Сохранённый username мог устареть ([A-007](../../audit/2026-09-16_application_audit.md)). Он используется только как начальное имя входа и не подтверждает владение аккаунтом. Смена username в Telegram не перезаписывает выбранный логин. Первая установка пароля и политика восстановления требуют отдельного подтверждённого процесса.
- `pass_hash = NULL` означает, что пароль не настроен. Записывать кодированный хеш сможет только будущий сервис парольной аутентификации. Слой сопоставления читает признак наличия хеша. Публичные ответы, логи, Dexie Cloud и текущий snapshot YDB хешей не получают.
- При будущей привязке Telegram сервер подтвердит владение обоими аккаунтами и заполнит `app_user_id` только в строке с `app_user_id IS NULL`. Операция должна проверить связь с подтверждённым `app_user.telegram_user_id` и атомарно примениться в D1. Существующая аналогичная привязка обрабатывается идемпотентно, конфликт другой привязки отклоняется без слияния. Уникальный внешний ключ и запрет подмены заполненной ссылки защищают от гонок и переноса связи. `ON DELETE RESTRICT` требует явного согласованного жизненного цикла удаления вместо молчаливой отвязки или удаления credential-записи. После привязки `user_id` и `tg:<user_id>` сохраняются.

#### Первичное заполнение

1. Штатный Worker deploy при merge применяет аддитивную D1-миграцию таблицы. Заполнение запускается отдельной согласованной операцией. Сначала выполнить [read-only preview](../../tools/cloudflare/password-credentials/preview.sql) и сверить суммарное количество аккаунтов, количество отсутствующих соответствий, невалидных ID и конфликтов ID/логинов. Отчёт состоит из чисел и не содержит персональных данных или хешей. При невалидном ID или конфликте ID остановиться и разобрать источник расхождения.
2. После согласования сохранить точку восстановления и зафиксировать список отсутствующих соответствий в защищённом контуре операции. Запустить [backfill](../../tools/cloudflare/password-credentials/backfill.sql) одним SQL-выражением. При записи заново вычисляются валидность, занятость имён и отсутствие привязки. Дубликаты и отсутствующие логины дают `NULL`, конфликт ID либо невалидный ID откатывает выражение целиком. Повторный запуск пропускает все уже связанные записи, в том числе ранее привязанные парольные.
3. Повторить preview и сверить разницу с числом вставок. Если во время проверки появились новые Telegram-аккаунты без соответствия, их можно обработать повторно. После завершённой записи при необходимости откатывается только согласованный набор созданных строк, под проверку исходных соответствий и отсутствия новых паролей, изменений логина и потребителей. При расхождении остановить откат и сохранить данные для разбора. Откат кода Worker сам по себе не требует удаления аддитивной таблицы.

#### Следующие этапы

1. Расширить существующую репликацию аккаунтов для будущей серверной парольной аутентификации на Yandex. Решение владельца от 2026-11-27: одна очередь D1, один полный снимок, одна таблица `account_replica` в действующей YDB. Ключ снимка соответствует постоянному `user_id`. Формат профиля `MeResponse` сохраняется, парольные данные хранятся как серверные колонки той же строки. См. [порядок развёртывания](../operations/yandex-account-replica.md#общий-снимок-профиля-и-учётных-данных).
2. Перевести браузерную сессию, выдачу и обновление Dexie-токенов на подтверждённое соответствие с постоянным `user_id`. Активация новых субъектов зависит от проверки всех потребителей в следующем этапе.
3. Перевести Telegram-интеграции с чтения суффикса `tg:<число>` на явный реальный `telegram_id`. Перепроверить ACL, relationship realms, локальную изоляцию и Media API до выдачи новых субъектов.
4. Подключить UI регистрации, входа и подтверждённой привязки после готовности серверного пути. Подключение создания соответствия при первом Telegram-входе выполняется в согласованном серверном этапе. В этапе 1 новый модуль и SQL первичного заполнения не вызываются действующими маршрутами.

## 3. Домены, DNS и HTTPS

**Бизнес-причина:** у `mezfit.ru` возникли сложности с подтверждением/идентификацией на Госуслугах. Домен **не удаляем**; в качестве основного выбираем `mezfit.online`. Не считать саму смену домена исправлением всех интеграций и авторизации.

Для каждого домена независимо:
1. Зарегистрирован/контролируется у регистратора; публичная Yandex Cloud DNS зона существует.
2. У регистратора NS делегированы на `ns1.yandexcloud.net` и `ns2.yandexcloud.net`; необходимо проверить DNSSEC/DS и фактическое делегирование через публичный DNS.
3. Точная запись `_acme-challenge.<домен>.` типа CNAME создаётся из значения managed Certificate Manager.
4. Сертификат имеет **`ISSUED`**; статус `VALIDATING` **не подходит** для подключения.
5. Отдельно подтверждённой операцией домен прикрепляется к **существующему** Gateway с этим сертификатом, а apex ANAME указывает на его техническое имя.
6. Проверяются реальный HTTPS/Host routing, API и клиентское поведение без VPN.

На 2026-11-23 пользователь сообщил, что **сменил NS, но распространение делегирования ещё не завершилось**. По последним рассмотренным логам обе CNAME для проверки добавлены в Cloud DNS, а сертификаты оставались в `VALIDATING`. Это **снимок состояния**, а не подтверждение текущего публичного DNS. Преждевременный `activate_online` корректно завершился ошибкой `certificate status is VALIDATING; require ISSUED`. Не обходить этот guard.

**Origin-изоляция:** `https://mezfit.online` и `https://mezfit.ru` имеют раздельные cookies, IndexedDB/Dexie-кеш и localStorage даже при общей Dexie Cloud БД. В конечном пользовательском опыте использовать **один канонический origin** `mezfit.online`, в том числе Telegram Mini App URL, OAuth callback/allowlists и публикуемые ссылки. `mezfit.ru` возможно оставить как дополнительный адрес/будущий серверный redirect 301, **но redirect ещё не реализован и требует отдельного решения** после проверки auth/ссылок. Не считать оба домена «одной браузерной сессией».

Точный оператор: [dual_domains.py](../../tools/yandex-infrastructure/dual_domains.py). Процедура: [yandex-dual-domains.md](../operations/yandex-dual-domains.md).

## 4. Telegram: две строго раздельные схемы аутентификации

### 4.1 Действующий Telegram Mini App

Источник доверия — подписанное Telegram `initData`; сервер проверяет подпись и устанавливает реального пользователя, а авторизация последующих привилегированных операций и Dexie Cloud realm/role constraints остаётся за сервером/существующими контрактами. Не переносить проверку в React. Пока Yandex `/api/*` не мигрирован, обычный браузер **не является полноценной заменой Mini App**.

### 4.2 Новый browser login — **PR #886, ещё не в `main` на дату записи**

Внешний браузер должен видеть `«Авторизация через Telegram»` и кнопку `«Войти через Telegram»`, а не исключительно требование открыть Mini App. Для этого выбран официальный **Telegram Login / OIDC** c Authorization Code + PKCE S256.

Планируемая реализация на Yandex:
- `GET /auth/start`: генерация случайных `state`/`nonce`/PKCE-verifier, краткоживущая подписанная cookie, redirect в Telegram.
- `GET /auth/callback`: серверный обмен code с OIDC Client Secret, проверка Telegram JWKS/RS256, issuer, audience, nonce, времени действия и Telegram identity.
- `GET /auth/session`: проверка подписанной `Secure; HttpOnly; SameSite=Lax` браузерной session-cookie; возврат только подтверждённой публичной идентичности.
- `POST /auth/logout`: требование совпадающего Origin и завершение браузерной сессии.
- Cookie привязана к hostname; сессия не означает доступ к Dexie Cloud, API, Coach/Client данным; никакой подделки `initData`.
- Приватная Cloud Function вызывается Gateway от имени разрешённого service account. Browser identity не получает bot secret, OIDC secret, privileged token или произвольный Cloud Function invoke.

**Внешняя настройка BotFather** для `@mezfit_bot`:
- Redirect URIs: `https://d5dnrvd45b0b0s0u95g3.3zvepvee.apigw.yandexcloud.net/auth/callback`, `https://mezfit.online/auth/callback`, `https://mezfit.ru/auth/callback`.
- Trusted Origins соответственно эти три `https://<host>` без пути; Native Login не требуется.
- `Signing Algorithm: RS256`. Client Secret — **не** Telegram Bot API token.

**Утверждённый способ хранения секрета (изменён после обсуждения):**
- GitHub Actions **Variable** `TELEGRAM_LOGIN_CLIENT_ID` = `8635045061` (публичный идентификатор).
- GitHub Actions **Secret** `TELEGRAM_LOGIN_CLIENT_SECRET` = секрет из BotFather; никогда не размещать значение в репозитории, обсуждениях, обычных Variables или логах.
- При `prepare/apply` workflow сам создаёт отдельный runtime SA, deletion-protected Lockbox, три ключа `client_id`, `client_secret`, `session_secret` (последний генерируется случайно), выдаёт только узкий `lockbox.payloadViewer` на этот секрет и публикует Node.js Cloud Function.
- ID SA/Lockbox/version определяются из API Yandex Cloud. Ручное заполнение Lockbox и отдельные Variables `YC_LOGIN_RUNTIME_SA_ID` / `YC_LOGIN_LOCKBOX_ID` / `YC_LOGIN_LOCKBOX_VERSION_ID` **не требуются**.
- Операции идемпотентны; автоматическая ротация/перезапись уже существующего секрета запрещены. Для ротации — отдельный утверждённый процесс.
- Разделить аккаунт GitHub-deploy от runtime identity. GitHub-deploy **не должен** регулярно читать содержимое Lockbox; широкий bootstrap-доступ ограничить по времени.

**IAM bootstrap:** создание SA, Lockbox, IAM bindings и функции требует предварительно назначенных прав у `mezfit-github-deploy`. В PR #886 указаны необходимые для bootstrap роли `iam.serviceAccounts.admin`, `lockbox.admin`, `functions.admin` (для Gateway сохраняется `api-gateway.editor`). При отсутствии прав будет 403; **workflow не может повысить себе права**. `lockbox.admin` чувствителен, поскольку даёт доступ к payload: после первоначальной установки оценить отзыв временного административного grant. Никаких ручных действий с самим OIDC секретом в консоли Яндекса не требуется.

**Функциональная граница PR #886:** после входа можно подтвердить браузерную личность и завершить сеанс, но **ещё нельзя работать с Coach/Client, тренировками, программами и Dexie Cloud**. Это требует следующего backend-среза с полноценными защищёнными API и проверкой realm ACL.

PR: [#886 — Telegram browser OIDC with Yandex server-side verification](https://github.com/buropotok/mezfit/pull/886). Документация в его ветке: `docs/operations/yandex-browser-telegram-login.md`. На момент фиксации PR **открыт**, исправляется CI; ничего из него нельзя описывать как уже развёрнутый production backend.

## 5. GitHub Actions: управляемое развёртывание

Общие правила ручных Yandex operator workflows. Для автоматического workflow реплики применяется исключение из YC-08 в §1.3.
- только `workflow_dispatch`, `main`, owner-restricted, read-only `Preview` по умолчанию;
- `Apply` отдельно и только после точного ключа; создавать недостающие ресурсы, не удалять существующие;
- GitHub OIDC → временный IAM token сервиса Яндекса, без долговременных ключей в GitHub;
- отсутствие прав → fail closed/403, не «исправлять» расширением ролей без решения владельца;
- readback-проверка ресурсов после мутаций; drift/конфликт → остановка и ручное разбирательство;
- локальные `npm`/`typecheck`/`test`/`build` не запускать вместо CI; тесты и билд выполняет GitHub Actions по правилам `AGENTS.md`.

## 7. Производительность: наблюдение, не установленная причина

Пользователь наблюдал **около 20 секунд** открытия SPA через технический Yandex Gateway и почти мгновенное открытие через Cloudflare Worker на мобильной сети (с VPN). **Корневой источник задержки не измерен:** на тот момент нельзя было открыть Network/DevTools.

Фактическая схема сейчас: `API Gateway → Object Storage` для HTML/JS/CSS, **без выделенного Yandex CDN для этой SPA**. Возможные, но **не подтверждённые** причины: RTT/сеть, TTFB Gateway/Object Storage, отсутствие/особенности HTTP-сжатия, вес JS/CSS, блокирующая загрузка Telegram SDK из `index.html`, запуск приложения. Смена hostname на `mezfit.online` сама по себе этот симптом не исправит.

Перед оптимизацией:
1. Снять холодную загрузку через Chrome Network: `document`/TTFB, JS/CSS transfer/size и Telegram SDK.
2. Сверить `Content-Encoding`, `Cache-Control`, `Content-Type` и Yandex Gateway latency.
3. Проверить Yandex URL и CF на **одном устройстве/одной сети**, с одинаковым VPN, холодным кешем.
4. Если узкое место в доставке статики — рассмотреть **Yandex CDN / сжатие / корректное кеширование** отдельным решением; не добавлять CDN «наугад».
5. Измерять отдельно время открытия HTML, загрузку приложения и проверку identity/API.

Этапы 1 и 2 работают, владелец подтвердил доставку учётных записей CF → YDB и первоначальное заполнение. Этап 3 требует отдельного [подключения webhook и проверки клиента](../operations/telegram-bot-invitations.md). После проверки следуют этапы 4–6 из §1.3.
2. Сохранять действующий Mini App, CF-регистрацию, Telegram Bot API и уведомления до проверки новых сценариев. После перехода на бот отдельно проверить, какие старые invitation handlers и экраны действительно больше не используются.
3. После запуска браузерного интерфейса поэтапно переносить необходимые прикладные API и технические операции, которые должны работать без VPN. Не переносить Dexie Cloud business CRUD/ACL в отдельную БД; не вводить синхронизацию бизнес-данных.
4. Аудировать CF D1/R2/Durable Objects, коммуникационные media, Yandex media signer и публичные объекты. Сохранить CF-контур регистрации и Telegram-интеграции. Выводить из эксплуатации только ресурсы без остающихся потребителей после отдельного решения и проверки отката.

6. Проверить фактические NS/DS, CNAME, TLS и canonical origin `mezfit.online`; отдельно согласовать redirect `.ru` → `.online`, если он нужен. Не повторять подтверждённый Apply только из-за старых статусов в §2–6.

**Открытые технические вопросы:** точные схемы YDB/outbox и протокол аутентификации CF → Yandex, первоначальное заполнение реплик, webhook и проверяемое подтверждение личности для браузерной регистрации, создание приглашения тренером вне VPN, перечень оставшихся маршрутов и CF-зависимостей, CDN/сжатие и окончательная политика redirect. Эти вопросы решаются в соответствующих ограниченных PR; новые архитектурные компоненты без подтверждённой необходимости не добавлять.

## 9. Инструкция следующему чату / агенту

1. **Сначала прочитать этот документ**, корневой [AGENTS.md](../../AGENTS.md), [local-first-storage-sync.md](local-first-storage-sync.md) и нужную профильную инструкцию из `docs/operations`.
2. Проверять актуальные `main`, PR и Actions: **PR merged ≠ Apply выполнен ≠ ресурс ACTIVE ≠ продукт работает**. Не переносить старые статусы сертификатов/CI на текущий момент.
3. Сохранять архитектурные границы: Dexie Cloud canonical, realm ACL и Telegram server-side identity; никакого второго authoritative store, no fake `initData`, no CF proxy как неявный workaround.
4. Работа в `buropotok/mezfit`: выполнить `AGENTS.md`, проверить исходники тестов и системные последствия, ознакомиться с `audit/`; не переписывать существующие тесты ради прохождения CI. После PR не ждать CI, кроме отдельного запроса пользователя на его анализ.
5. Следовать YC-13–YC-16 и порядку §1.3; сохранять отдельные границы auth, регистрации, репликации и запуска UI. Перед коммитом в существующий PR проверять, что он открыт; не коммитить в закрытые PR.
6. Не запрашивать и не печатать секреты. Из GitHub допускаются только названия Secrets/Variables, но не их значения. Для ручных операций требуется явный owner-confirmed Apply. Для автоматического Apply реплики разрешением является проверенный merge в `main` согласно §1.3.
