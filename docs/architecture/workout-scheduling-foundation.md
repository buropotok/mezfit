# Workout scheduling

Status: occurrence-backed calendar with private local drafts and privileged booking.

## Scheduling integration (current)

- The `ProgramDay` is a template, never the live plan of a booked workout.
- A user creates a local `localWorkoutOccurrenceDrafts` record (introduced in Dexie v9, retained in v10,
  `unsyncedTables`). It contains a deep PLAN snapshot, the program origin,
  UTC slot and workout format. Drafts do not enter Dexie Cloud, consume confirmed
  slots or become visible to the client on another device.
- The schedule timeline merges authorized `workoutOccurrences` from the Dexie
  Cloud Addon with the current device's private drafts. A coach's calendar only
  includes coached assigned occurrences and personal workouts. A client's
  calendar includes all their assigned and personal workouts. Calendar rows
  remain visible even if the source day is later deprecated.
- Editing exercise selection, order or set count is restricted to the original
  program author. The set-metric editor is deliberately a placeholder in this
  iteration. PLAN snapshots include exercise definitions, set recommendations
  and attached links.
- User action `Save` submits a versioned intent, identified by the draft's
  stable request key, to the authenticated Worker. A globally addressed Durable
  Object serializes structural authorization/idempotent create/readback for all bookings, using
  the existing server-only Dexie Cloud membership credentials. The server alone
  POSTs `workoutOccurrences`; `@id` is generated by Dexie Cloud. Confirmation
  is retried idempotently using `sourceRequestId`, an immutable submitted-command
  fingerprint and remote readback. A retry is not compared with mutable booking
  PLAN/time/status; the API returns a confirmation receipt, not lifecycle state.
- The Worker verifies the Telegram actor and approved
  membership, operation permissions, exercise ownership/access and payload
  format. It never trusts declared identity/realm without structural authorization.
  It does not re-read cloud program/day/phase state, compare PLAN with a cloud
  template, enforce archive/deletion state, or search cloud calendar conflicts.
  Program/phase eligibility and slot checks belong to local action acceptance.
- The source `ProgramDay` is updated only on author consent, with a local-first
  transactional comparison against the original template. If booking or this
  opt-in update fails, the draft is retained for a retry.
- The booked `WorkoutOccurrence.plan` is independent of subsequent changes
  to the program. Future Dexie workout-session Start must read this PLAN and
  produce independent session PLAN/FACT; the existing legacy D1 workout-session
  path is **not** migrated by the scheduling UI cutover.
- The old synchronized booking-intent table and its repository are retired.
  Booking uses the authenticated Worker request directly; local drafts remain
  private and durable until confirmation.

## Validation boundaries

The booking request carries a structural access envelope (realm, athlete, coach,
client), separately from source program/day IDs and the self-contained PLAN.
The Worker proves personal identity or exact relationship membership using this
envelope. Source IDs do not grant access and need not have synchronized yet.
A locally accepted draft remains valid after local or cloud source status changes.

Every exercise snapshot is structurally decoded. Public definition access and
known custom-definition ownership are checked without comparing names, media,
archive state or PLAN content. An author-attributed complete custom snapshot
may arrive before its definition; this stores submitted content, grants no
private reads and never creates/changes the catalogue definition. Known foreign
ownership or attribution is rejected. No cloud business state is normalized
back into the received PLAN. See AGENTS.md §10 for the governing rule.

## Storage and time

Local schema v10 explicitly drops the retired `workoutScheduleRequests` table
when upgrading from v8/v9. Historical schema declarations are retained solely
for that local upgrade. PLAN, occurrences, FACT and private drafts are preserved.
The cloud table may remain inert: this retirement never deletes cloud business
records or changes the cloud schema. No provisioning path can recreate it.

Store canonical UTC `startsAtUtc` plus `durationMinutes`. Calendar display splits
an overnight workout at each local midnight. Local input rejects nonexistent or
ambiguous wall times during daylight-saving changes. The end time is resolved
on its actual local calendar day before calculating elapsed UTC minutes.

## ACL retirement and deployment

`cloud/roles.json` no longer grants either role permission to add intent rows.
Worker membership provisioning and the relationship operator require that exact
policy and reject the old grant. Coach PLAN and shared FACT grants are unchanged.

If the earlier ACL was applied, after merging run the protected manual
`dexie-retire-scheduling-acl.yml` workflow on `main`, first with
`operation=preview`, then `operation=apply` and confirmation
`REVOKE_SCHEDULING_COACH_CLIENT_ACL`. It accepts only the exact old policy or
an already retired policy. It removes only the old add grant and restores the
role descriptions, rechecks configuration immediately before import, and reads
back schema and every role after an attempted write. The existing protected
publisher is used; schema, other roles, PLAN/FACT grants, memberships and
business data cannot be changed. Remove this one-time operator after retirement
has been verified. It cannot restore or grant the retired permission.

Code deployment does not apply cloud permissions. In this nonproduction
rollout, membership provisioning intentionally fails closed until the exact
cloud ACL is installed. Complete the protected retirement before verifying new
invitations and two-account access. PR CI never mutates cloud configuration.

## Calendar interaction corrections

The timeline card always identifies the athlete (name and photograph). Its first
row reserves space for the complete draft badge; its second reserves space for
the complete time range before the ellipsized day name. The planning editor uses
the PLAN owner's identity. The future Start action is not part of this change.

A saved occurrence opens the existing PLAN editor through a private local draft
with targetOccurrenceId; submission updates that occurrence rather than creating
another. Completed/in-progress records remain viewable, with lifecycle eligibility
checked locally. Moves and resizes use the same mutation path; deletion cancels
the occurrence. Mutations preserve the immutable source booking identity and
carry a separate command identity for retry/readback. The Worker authorizes the
target realm/participants and writable fields, never current business statuses,
source templates or slot availability. Clients can change their independent
booking's time but cannot change coach PLAN content. Cloud roles/schema are unchanged.

Overlap is checked locally against the athlete and, for coached sessions, coach
calendars, private drafts and acknowledged records awaiting Addon projection.
The timeline accepts a resource predicate so unrelated athletes' independent
sessions do not block each other. It retains the existing touch/drag/resize
mechanics. Repeated uncertain submissions preserve the accepted command.
