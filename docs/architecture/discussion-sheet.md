# COMM-05: интерфейс одной ветки

Задача: [#640](https://github.com/buropotok/mezfit/issues/640).
Фундамент: [DiscussionRepository](discussions-repository.md), COMM-04 / PR #658.

## Граница и подключение

`src/discussions/index.ts` экспортирует `DiscussionSheet` и его typed props.
Вызывающий экран передаёт существующий account-owned `DiscussionRepository`,
`threadId`, canonical `anchor`, необязательный `focusMessageId`, `opened`, `onClose`,
`resolveAuthor`, `parentNavigation` и штатный `onNavigationContextChange` shell.
`resolveAuthor` использует уже доступные профили/аватары; sheet не загружает их по HTTP.
`parentNavigation` — стабильный snapshot контекста исходной сущности либо null.
Callback shell тоже должен быть стабильным. Пока sheet открыт, его callback Back
поочерёдно закрывает confirm, меню, режим composer, затем sheet; cleanup возвращает
ровно переданный parent. Переходить к другой сущности при закрытии не нужно.

Вход из push сначала разрешает точный anchor под существующим navigation owner,
потом передаёт sheet тот же thread/focus. Sheet не создаёт ветку, не заменяет source ID
и не реализует ещё один Telegram/browser-history handler. Исчезнувший источник
может сохранить разрешённую историю: header использует repository title snapshot.
Не найденный thread в данном anchor и недоступное сообщение дают безопасную ошибку.

В COMM-05 нет входов из меню сущностей, inbox, регистрации push или новой navigation
системы. Это интеграции COMM-06/07/08/12. Компонент не монтируется массово и не меняет
account factory/provider в историческом COMM-05. Уточнение COMM-06 ниже заменяет
opt-in: схема v17 регистрируется обычной поставкой.
Нельзя включать опцию на другом экземпляре той же account DB лишь ради открытия UI:
весь lifecycle аккаунта должен использовать согласованную версию схемы.
Schema/ACL Apply, membership, PLAN/FACT и business repository CRUD не меняются.

## UI и одобренное расширение

Используются Konsta 5.4.0 `Messages`, `MessagesTitle`, `Messagebar` и штатные
Mezfit BottomSheet/Dialog/LiquidPopover в iOS dark окружении приложения.
Messagebar использует узкий Konsta 5.4.0 адаптер в `src/ui/konsta-mezfit`:
сохраняются native toolbar, textarea, left/right слоты, события и анимации, но
textarea подстраивается под контент до пяти строк, затем прокручивается внутри.
Его публичный root ref измеряет место, резервируемое в собственном
scroll-контейнере sheet; сообщения при прокрутке остаются под compositor.
Композитор перекрывает их отдельным GlassSurface с действующими
`preset/optics/blur`, без собственных настроек материала.
Контекст reply/edit расположен над ним.
`visualViewport` resize/scroll и window resize меняют только публичные layout props
BottomSheet и отписываются при unmount. Safe areas остаются у штатных Sheet/Toolbar.

Владелец отдельно согласовал узкий `src/ui/konsta-mezfit/Message.tsx` перед реализацией.
У публичного Konsta Message ref указывает на всю строку, а bubbleRef/слота source нет.
Адаптер сохраняет его 5.4 renderer, классы, цвета и 70% ограничение, предоставляя
только `bubbleRef`, `onBubbleClick`, `bubbleSource`. Renderer-capable name/textHeader/
textFooter типизированы как ReactNode (в upstream declarations они string).
Сравнительный тест проверяет фактическую разметку адаптера и native Message.
Файлы установленного Konsta не меняются. Feature-код не обращается к private DOM/CSS.

LiquidPopover получает прозрачный неинтерактивный круг 4×4 в центре bubble и актуальные
`preset/optics/blur` из переданных GlassSettings либо существующего browser settings.
Источник находится внутри bubble; его координаты автоматически следуют layout/scroll.
Меню одно. Его portal-события останавливаются в собственном composition wrapper,
чтобы действие/backdrop не открывали bubble menu повторно.
Tabler `arrow-back-up` добавлен в общий реестр; edit/copy/trash переиспользуются.

Ответ использует repository `replyToMessageId`; отображаемая quote — текущая проекция,
не отдельная сохранённая копия. Заголовок автора и первая строка с CSS ellipsis
принадлежат контенту Mezfit. Tombstone/недоступность не показывают прежний текст.
Edit работает в том же composer, remove — после штатного confirm; copy читает полный
доступный текст через repository и использует Clipboard API с честной ошибкой отказа.
Для будущих медиа есть `renderAttachment`, сейчас без загрузки, confirm или storage URLs.

## Жизненный цикл и история

`DiscussionSession` — application owner живых UI-проекций, не бизнес-хранилище и не
SyncEngine. Он использует только public repository methods. Каждая страница имеет
свою subscribe/unsubscribe; при сдвиге курсора пересоздаются зависимые страницы,
в том числе ещё не завершившие первую загрузку. Закрытие/смена repository/target
отменяют старые результаты. Locate сверяет exact message через getMessage, подгружает
нужные страницы через observePage и подтверждает успех только при наличии точного ID
в актуальной live-проекции. Нет повторного сканирования тех же страниц отдельно от observer. UI прокручивает только
собственный scroll owner и ненадолго подсвечивает собственную оболочку строки.

Подгрузка вверх сохраняет позицию по разнице scrollHeight. Новые сообщения ведут
к концу только когда читатель уже был у конца. При старом focus target автоматического
прочтения всей новой истории нет; markRead вызывается у конца для чужих сообщений.
Send retry сохраняет подготовленную команду с тем же ID; двойной submit блокируется
владельцем операции. Локальный успех независим от sync status/error/retry готового
COMM-04 helper. Нового transport/очереди или фоновых HTTP из React нет.

При отправке вложения его Blob сохраняется в IndexedDB аккаунта до запроса к
Object Storage. Существующий приватный черновик сохраняет идентификаторы сообщения,
вложения и объекта. Лента показывает локальное превью во время загрузки и после
ошибки. Отмена прерывает запрос, оставляя файл для повтора. После открытия чата
прерванная отправка восстанавливается из черновика и локального Blob. Повтор
использует те же идентификаторы. Публикация по-прежнему выполняется существующей
транзакцией после успешной загрузки. До публикации собеседник сообщение не видит.

### Сохранение опубликованных вложений

В меню сообщения доступны «Ответить» и «Сохранить» для опубликованных,
не удалённых фото, видео, видеокружков и голосовых сообщений независимо от
автора. При нескольких вложениях каждое имеет отдельное действие сохранения.
«Редактировать» и «Удалить» остаются только для собственных сообщений.
Стандартный LiquidPopover, MezfitDialog и примитивы медиа не изменяются.

Диалог сохранения переиспользует проверенную локальную media cache и штатный
`downloadDiscussionMedia` (Yandex GET с авторизованным R2 GET fallback при
подходящем опубликованном attachment identity), не добавляя выдачу новых прав,
сервисов, ACL или хранилищ. При отсутствии сохранённого исходного имени файл
получает название Mezfit с расширением по MIME. Экспорт использует системное
меню устройства либо штатный Telegram downloadFile/загрузку Blob с честной
обработкой отказа. Локальное неотправленное видео сохраняет прежний сценарий.
Проверка реальных Android/iOS Telegram WebView остаётся частью приёмки.

### Жест ответа по сообщению

Опубликованные сообщения, фотографии, видео, голосовые и видеокружки поддерживают
свайп **влево** для ответа. Строка сообщения непосредственно следует за пальцем,
смещаясь максимум на 100 CSS px. Ответ применяется один раз при отпускании пальца
с сохранённым смещением от 60 px; ниже порога и при отмене жеста смещение
возвращается на место без выбора reply. Жест игнорирует вертикальную прокрутку,
движение вправо, удалённые сообщения и несовместимые режимы composer.

UI-владелец `DiscussionSwipeReplyRow` повторно использует тот же typed
`replyToMessage` сценарий, что действие «Ответить» в `LiquidPopover`, включая
смену Edit → Reply и явную отметку просмотра чужого сообщения. Видеокружок
выводится в playback-портал, поэтому его визуальный круг получает то же
смещение через React context, без поиска внутренних DOM Konsta и без
изменения скроллера или медиа/репозиториев. Для iOS/Android WebView
строка сообщения обрабатывает нативную цепочку `touchstart/touchmove/touchend`:
пока касание активно, временный `touchmove` listener c `passive:false`
блокирует **только распознанное горизонтальное** перемещение. Это необходимо,
поскольку WebView может завершить PointerEvent-поток (`pointercancel`)
раньше касания, из-за чего пузырь преждевременно возвращался. Нативный
вертикальный скролл, движение вправо и `touchcancel` не отправляют reply.
Листенеры снимаются при окончании/отмене жеста, отключении строки и unmount.
Pointer Events остаются fallback для других указателей.

Визуальная подсказка по видеообразцу — круглый полупрозрачный индикатор
с белой сплошной стрелкой `reply-solid`, векторизованной из пользовательской
PNG в `src/ui/icons/reply-solid.svg` и зарегистрированной в штатном UI Kit Icon.
В существующем `bubbleSource` индикатор размещён **справа от
смещённого пузыря**, в отдельной области шириной `d`, где `d` — расстояние
свайпа (0–100 CSS px). Область начинается на правом краю текущего пузыря,
а заканчивается в его первоначальном положении. Центр круга находится
ровно посередине этой области: пузырь проходит 100 px, а индикатор
перемещается на 50 px. При отпускании обе части возвращаются за 180 ms
с одинаковым `ease-out`; видимость индикатора убывает обратно. Пока
порог ещё не достигнут, прогресс размыкается при обратном движении.
После замыкания линия прогресса не возвращается до следующего жеста.

Нормальный диаметр круга — **34 CSS px** (одна Chat-строка 22 px + Konsta
iOS padding 6 px с каждой стороны). Круг и внешний SVG-прогресс
ограничены `max(0px, min(34px, d - 8px))`: до появления достаточного
пространства они уменьшаются, а между внешним краем кольца и пузырём
остаётся минимум **4 CSS px** при любой видимой ширине. У расширенного
кольца предельный диаметр **51.68 px** (152% от 34 px), но он тоже
ограничен `d - 8px`. Высота контейнера 52 px допускает полный pulse
без вертикального обрезания. Белая стрелка живёт внутри отдельной
обёртки размером максимум 15 px: не касается кольца, её геометрия
и фон круга не меняют Konsta. Фон полупрозрачный.

Кольцо заполняется до 100% на **60 CSS px**. При первом достижении порога
в текущем жесте **та же самая замкнутая SVG-линия** превращается в
расширяющееся кольцо: за **300 ms** она увеличивается до 152% (51.68 px)
и исчезает через opacity. Второе кольцо не создаётся, фоновый ободок
сразу скрывается. После начала расширения прогресс/ободок остаются
скрыты до следующего жеста, даже если палец вернулся ниже порога или
жест завершился. Расширение не зависит от отпускания и не повторяется
при повторном пересечении 60 px в одном касании.

Ровно при первом замыкании также выполняется
`runHapticProbe('telegram-success-notification')`: запрос Telegram
`HapticFeedback.notificationOccurred('success')` возвращает `sent`,
когда API доступен и принял вызов. Отсутствие/ошибка Telegram haptic
не влияет на жест. `touchend/pointerup` запускает обратную анимацию;
ответ отправляется только при отпускании на 60 px или дальше. При
отмене ответ не отправляется. Декоративный индикатор (`aria-hidden`,
`pointer-events:none`) не является кнопкой. При reduced motion
расширение сокращено до 1 ms; механика жеста и репозитории не меняются.

Та же точная Telegram success notification без fallback-вибрации
отправляется при каждом успешном переключении режима ГС ↔ Кружок
в `DiscussionSheet`, а также однократно в общем
`useRecordingGesture` при переходе **активной** записи в `locked`
после свайпа вверх (для обоих режимов). Ни простой тап на кнопку
записи, ни удержание до старта, ни повторные движения уже
заблокированной записи не вызывают дополнительного success-отклика.

Настоящее iOS/Android WebView поведение остаётся отдельной частью приёмки.

## Исправления системного ревью COMM-01–05

Живая история сохраняет нижнюю границу уже раскрытых страниц, а не только их
количество. При сдвиге курсоров подгружаются дополнительные страницы до этой
границы; отображаются актуальные repository rows, включая tombstones. UI сохраняет
видимую строку и её смещение внутри собственного scroll owner, когда читатель
находится вне конца.

Реальный DiscussionRepository предоставляет getDraft/saveDraft. Composer читает
приватный черновик по ветке при открытии и сразу ставит локальное сохранение
каждого изменения текста/reply перед последующим send или закрытием. Ошибки
восстановления блокируют ввод до retry; ошибки сохранения показываются с retry.
Закрытие отменяет только UI completion, уже начатые локальные записи завершаются.
Редактирование отправленной реплики не переписывает отдельный неотправленный
черновик. После успешной отправки composer очищается, ID для retry сохраняется.
Публичный DiscussionPort требует draft API существующего repository;
отдельного UI-хранилища или необязательного режима без persistence нет.

Новые регрессии покрывают точную границу 80→81, входящий burst, retry и live delete,
закрытие/восстановление текста/reply/ID, ошибку восстановления и удержание scroll.
Физическая приёмка Telegram iOS/Android и прочие rollout gates остаются обязательными.

Уточнение после review PR #662: переход Edit→Reply сохраняет отдельный текст
черновика, а не временный текст редактирования. Если сохранение обнаружило, что
ID уже опубликован с другого устройства, composer сохраняет последние изменения
под новым ID. Запоздалые отказы старого ID не меняют этот новый черновик. При
гонке публикации непосредственно перед Send текст не очищается; после локального
сохранения нового черновика пользователь может повторить отправку.

## Мобильный визуальный режим и статусы COMM-05

`showAvatars=false` — компактная личная переписка по умолчанию; `true` —
тот же renderer с именами и аватарами для будущей группы. Время находится
внутри bubble; адаптер `MezfitMessage` резервирует его место в текстовом
контенте, отдельно от цитаты. Входящая реплика показывает только время.

Для собственных сообщений UI получает **не общий статус Sync**, а два сигнала
репозитория: `confirmDelivery(threadId, messageIds)` запоминает подтверждённые
ID только после awaited Dexie Cloud push и проверки видимости каждой записи;
`observeReceipts(threadId)` реактивно читает `readThrough` других участников
из существующей таблицы `discussionReadStates`. Двойные галочки доступны
только по валидному watermark другого пользователя, одна — по подтверждённой
отправке конкретной записи. Отсутствие доказательства не превращается в
фиктивную доставку; память подтверждений восстанавливается новым
проверочным push после открытия. Новых таблиц/ACL/Worker/SyncEngine нет.

UI Kit использует тот же `DiscussionSheet` и in-memory port; его receipts
искусственные и прямо маркированы «Демо». Приёмка на настоящих Android/iOS
WebView с физической клавиатурой и визуальной проверкой стекла, safe areas и
скролла остаётся отдельной от CI source-tests.


## Уточнение COMM-06 (2026-11-07)

Из сущности сразу открывается одна переписка пары/anchor. Back/Close возвращают
к смонтированному источнику, списка тем и ручного создания больше нет.
Заголовок использует contextLabel; дублирующая капсула над сообщениями удалена.
Наблюдение реального recipient read-state привязано к storage thread сообщения,
включая объединённую legacy историю. Отметка прочтения выполняется только в
видимой переписке, поддерживает просмотр истории и явный retry при ошибке.
См. актуальную модель в discussion-entity-entry-points.md.

Уточнение индексов COMM-06: локальная v17 добавляет только `[id+lastReadAt]`
для условного обновления legacy read-state. Таблицы/поля/cloud ACL не меняются;
upgrade выполняется при обычном открытии account DB.
