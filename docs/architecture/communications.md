# Mezfit communications — нормативный контракт

**Статус:** нормативный продуктовый контракт; текстовые обсуждения и точки входа COMM-03–07 реализуются по связанным документам. Медиа, общая лента и push остаются отдельными этапами.

**Дата решений:** 2026-11-06; уточнение одного диалога и COMM-06/07/08 — 2026-11-07.

**Источник продуктовых решений:** [issue #636 / COMM-01](https://github.com/buropotok/mezfit/issues/636). При конфликте прежних документов применяются решения этого issue.

**Область MVP:** Telegram Mini App, Coach / Client, контекстные обсуждения, медиа и уведомления.

**Заменяет:** Telegram-centric концепцию от 2026-10-18 и редакцию этого документа от 2026-11-05.

**Связанные контракты:** [AGENTS.md](../../AGENTS.md), [local-first-storage-sync.md](local-first-storage-sync.md), [product invariants](../product/invariants.md), [typography.md](../../typography.md).

## 1. Граница текущего PR и MVP

COMM-01 зафиксировал продуктовый контракт. COMM-03–06 добавили схему/ACL, typed repository, DiscussionSheet и входы программы/плановой. COMM-07 добавил входы фактической тренировки, её упражнения и подхода для Coach/Client, сохраняя PLAN/FACT. COMM-08 подключает общий список диалогов, нижнюю навигацию и вкладку клиента. Наличие реализации или configuration readback не означает проверенную работу двух реальных устройств и доступность медиа без VPN.

MVP работает внутри Telegram на Android и iOS. Вход — только Telegram, несколько устройств одного пользователя поддерживаются. Самостоятельной публичной web-версии нет. Обычная web-точка загрузки HTML/JS/CSS Mini App существует и требует отдельной проверки холодного старта без VPN. Capacitor — будущий клиент: сохраняем границы платформенных адаптеров, но не реализуем нативный вход, плагины или push сейчас.

География пилота — Россия. Расчётная верхняя граница: 100 тренеров × 50 клиентов = 5000 отношений; объём и трафик видео пока неизвестны. Пилот начинается с двух тренеров и нескольких клиентов, затем расширяется до нескольких десятков клиентов. Только бесплатные либо явно одобренные расходы; бесплатность подтверждается текущими квотами и измерениями, не предположением о тарифе.

## 2. Продуктовый принцип и четыре уровня

Сообщения принадлежат одной канонической ветке конкретного объекта. Меню сущности, общая лента и вкладка клиента — проекции этих же данных. Свободная переписка вне контекста остаётся вне MVP; приложение не читает личные Telegram-чаты.

| Уровень | Допустимый объект | Граница |
| --- | --- | --- |
| Программа | Программа целиком (`CloudTrainingPlanRow`) | Нет веток у фазы, дня, упражнения или подхода шаблона программы |
| Тренировка | Конкретная запланированная occurrence либо самостоятельная session | Выполненная из occurrence тренировка сохраняет тот же контекст |
| Упражнение тренировки | Конкретный экземпляр внутри occurrence/session | Каталожное упражнение и шаблон программы не являются anchor |
| Подход тренировки | Конкретный экземпляр внутри упражнения occurrence/session | Номер подхода и source program ID не являются идентичностью |

**Одна сущность — одно обсуждение внутри конкретной пары тренер–спортсмен**
(уточнение COMM-06, 2026-11-07). Контекст внутри линейной переписки участники
формируют ответами и цитатами. Списка тем и ручного создания веток нет.
Вход из сущности немедленно открывает DiscussionSheet, автоматически создавая
или переиспользуя каноническое обсуждение. Заголовок показывает название сущности;
старые title snapshots остаются историческими данными, не идентичностью.

Старые ветки того же anchor и той же пары доступны в единой хронологии без
переноса или копирования сообщений. Сохраняются message/thread IDs, ответы,
вложения, авторство и read-state. Новый текст отправляется в детерминированный
канонический thread. Другой anchor/realm никогда не включается в эту историю.
Личные обсуждения остаются в личной области.

Все сообщения и вложения создаются через вход обсуждения соответствующей сущности.
В деталях программы — круглая message-circle под аватаром владельца; в списке
программ и плановой тренировке — пункт «Обсуждения» существующего меню.
Отдельного коммуникационного редактора в PLAN/FACT нет.

## 3. Выбранный реестр идентичностей и parent anchor

Уточнение COMM-03: **типизированный DiscussionAnchor и детерминированный ключ** в существующем realm. Для MVP отдельная таблица реестра/alias не нужна: ссылки occurrence/execution уже хранятся в доменных строках. Ключ связывает реальные ID с одним коммуникационным контекстом, не создавая второй снимок тренировки или отдельную систему синхронизации.

| Вид | Канонический ключ в области отношения/realm | Parent anchor и alias |
| --- | --- | --- |
| Программа | `program + trainingPlanId` | Родителя обсуждений нет; дочерние шаблонные записи исключены |
| Плановая и её execution | `workout + occurrenceId` | `adHocSessions.occurrenceId` связывает session с тем же anchor, не с новым |
| Самостоятельная тренировка | `workout + sessionId` с отдельным типизированным namespace session | Нет occurrence; связь с программой — provenance, не общая identity |
| Упражнение плановой | `workout anchor + occurrence exercise ID` | Parent — workout; execution alias через `occurrenceExerciseId` |
| Подход плановой | `exercise anchor + occurrence set ID` | Parent — exercise; execution alias через `occurrenceSetId` |
| Упражнение/подход без occurrence-происхождения | `session namespace + exerciseId / setId` с реальными parent ID | Parent — конкретная workout/exercise; не угадывать по позиции |

Реальные связи уже представлены в `src/data/cloud/adhoc-workout-types.ts` и материализуются в `src/data/cloud/adhoc-workouts.ts`: session содержит `occurrenceId`, exercise — `occurrenceExerciseId`, set — `occurrenceSetId`. COMM-03 сопоставляет эти пути и отдельно обрабатывает legacy FACT-модели. Legacy aliases добавляются только при доказанной связи; при отсутствии доказательства объект явно недоступен, а не перепривязывается к одноимённому подходу. Два устройства получают одинаковый ключ из тех же ID; один ключ пары/anchor определяет одно обсуждение. Конкретные контракты и индексы определены в COMM-03.

Anchor/context принадлежат области thread с `realmId` и `coachClientId` либо явной личной области; каждая message/read-state/attachment строка содержит свой `realmId` и точную ссылку на parent. Parent и alias неизменяемы и проверяются типизированным репозиторием; refs не дают прав. Ветка всегда ссылается на один canonical anchor. Context path содержит типизированные ID для перехода и группировки, а не дополнительные разрешения. Связь с программой у тренировки — provenance: обсуждения исторических тренировок не превращаются в ветки элементов шаблона.

Порядок, название, архивирование и логическое удаление не меняют anchor. Копия программы/тренировки получает собственные anchors; сообщения оригинала не копируются автоматически. Для удалённого исходного объекта сохраняется разрешённая история с честным состоянием «объект недоступен», без перехода к другому объекту.

Обсуждения двух тренеров изолированы разными отношениями и shared realms. Личная область клиента не публикуется при подключении тренера. Историческая программа сама по себе не открывает тренеру личные обсуждения до подключения; наличие program/source ID не даёт такого доступа. Новая связь не наследует старую переписку автоматически. По уточнению владельца в issue #638 от 2026-11-06 бывшие участники сохраняют доступ к своей прежней совместной истории и вложениям, пока они хранятся (§10). Завершение отношений не передаёт эту историю новому тренеру и само по себе не отзывает исторический доступ.

## 4. Сообщения, ответы и непрочитанные

- Сообщение имеет стабильный ID, автора, время, текст и/или вложения. Допустимо вложение без текста.
- **Ответ на конкретное сообщение обязателен:** `replyToMessageId` внутри той же ветки, компактная цитата/ссылка и переход к исходной реплике. Это линейный чат, а не вложенные деревья.
- **Редактирование и удаление сообщений обязательны**; история редактирования не нужна. COMM-03/04 должны описать серверно проверяемые права автора, минимальные mutable-поля и tombstone-поведение, не выдавая право менять чужой текст. Удаление не должно оставлять читаемый текст в цитате или создавать битый jump; для удалённого/недоступного оригинала показывается честный placeholder.
- Нет реакций, пересылок, сложных цепочек и назначенных задач.
- **У ветки нет бизнес-статусов `open`, `resolved`, `requiresReply`.** Прочитал и не ответил — ответственность участника, не новая задача или эскалация.
- У каждого участника собственные непрочитанные, согласованные между его устройствами. Прочтение другого участника их не сбрасывает. Технические состояния локального сохранения/синхронизации/загрузки медиа не являются статусами обсуждения.

Не дублировать реплики в родителях, ленте, карточках клиентов или Telegram. Не хранить производные unread-счётчики как независимый источник истины. Точный read cursor, порядок сообщений и защита от регресса cursor при синхронизации разных устройств проектируются в COMM-03/04.

## 5. UX и навигационный контракт

В меню сущности пункт «Обсуждения» имеет **надстрочный индекс непрочитанных как в Telegram**. При закрытом меню тот же индекс находится около `…`. Число веток не подменяет число непрочитанных сообщений. В карточке сущности **нет превью текста, видео или последней реплики**. Родительские проекции могут группировать доступные ветки по устойчивым parent ID без копирования сообщений и создания веток у шаблонных дочерних объектов.

Обсуждения сразу открываются в **DiscussionSheet** с линейной перепиской и автоматическим идемпотентным созданием. Основа — закреплённая **Konsta Messages 5.4.0**, тема iOS + dark.

| Публичный примитив | Назначение |
| --- | --- |
| Messages | Лента открытой ветки |
| Message | Входящие/исходящие реплики, имя, аватар, метаданные |
| MessagesTitle | Даты/разделители |
| Messagebar | Ввод текста и слоты действий |

Использовать публичные props/slots и утверждённый слой `src/ui/konsta-mezfit`; установленные файлы Konsta и механику примитивов не менять. Прикладной плеер, цитата и состояние вложения — контент Mezfit. Запись, загрузка и отправка не предоставляются самим Messages. Ограничения ширины сообщений, авторазмера ввода, клавиатуры и safe areas проверяются в COMM-05; недостающую возможность публичного/адаптерного API сообщить владельцу, не обходить feature CSS/DOM. Типографика — по `typography.md`.

В открытой переписке есть компактный контекстный заголовок. Дублирующей капсулы с названием над сообщениями нет; Close и Back возвращают к смонтированному исходному экрану. Обратный переход из общей ленты/ветки восстанавливает её workout/exercise/set по canonical anchor; из меню сущности доступна та же история.

Общий раздел **«Обсуждения» — нижняя вкладка обеих ролей**. Прежний пункт «Программы» переносится из нижнего таббара в Navbar-меню. На странице каждого клиента у тренера появляется дополнительная вкладка обсуждений этого клиента.

Общий раздел — разделённый список диалогов через UIkit List/ListItem с контекстом и unread; канонический чат не размножается на ленты. Одна сущность в одной паре отображается одной строкой; старые headers проецируются совместно без переноса сообщений. Tap открывает тот же DiscussionSheet, отдельный ListItem.trailingAction — точную сущность. Фильтры: **клиент у тренера и даты у обеих ролей**. Статус-фильтров нет. Дополнительные фильтры, отдельный поиск или новая модель задач не являются требованиями MVP. Все проекции ограничены правами текущего пользователя.

Переход из уведомления — одна операция навигации с `{anchorId, threadId, messageId}`: проверить доступ, открыть **точную сущность**, автоматически раскрыть Bottom Sheet, открыть ветку и прокрутить к **точному сообщению**. При асинхронной гидратации дождаться нужной локальной проекции под владельцем навигации, отменять устаревший переход. Закрытие шита оставляет пользователя на сущности. Telegram BackButton и внутренний Back используют единый маршрут. При удалённом сообщении/объекте или отсутствии прав показать безопасное объяснение без утечки чужих данных и без перехода к соседней сущности.

## 6. Данные и local-first границы

Это **логическая модель будущего контракта**, не готовая миграция или разрешение на новые grants:

| Сущность | Содержание |
| --- | --- |
| DiscussionAnchor (внутри thread) | Каноническая identity, parent path и ключ по реальным source ID, без отдельной таблицы |
| DiscussionThread | id, realm/отношение, anchorId, автоматический title snapshot, createdAt, lastActivityAt; без бизнес-статуса |
| DiscussionMessage | id, realm, threadId, authorUserId, text, replyToMessageId, createdAt, editedAt/deletedAt |
| MessageAttachment | id, realm, messageId, owner=authorUserId, mediaType, storageKey, mime/размер/длительность, uploadState, confirmedAt, deletedAt? |
| DiscussionReadState | threadId, userId, cursor прочтения в собственной области записи участника |

Путь: **React → типизированные application/domain repositories → локальная Dexie-транзакция → Dexie Cloud Addon → Dexie Cloud**. IndexedDB содержит разрешённый рабочий subset; Dexie Cloud — единственная бизнес-БД. Нормальные сообщения и правки принимаются локально без ожидания HTTP/cloud push. Addon владеет репликацией и повторами; отдельного чат-backend CRUD, второго SyncEngine, change-feed или теневой БД в Yandex нет. Серверная проверка структурного доступа не должна заново проверять динамическое состояние PLAN против отставшей облачной копии.

Shared realm относится к конкретной паре тренер–клиент. Каждая строка получает корректный realm/owner; ссылки на родителя и UI-фильтр не заменяют ACL. Проверять thread/anchor/parent/author/realm типизированным репозиторием; серверные гарантии ограничены realm membership и штатным owner согласно согласованному исключению ниже. Чтение чужих media keys не разрешено знанием ключа. Личные заметки и приватные черновики не публикуются автоматически. Проверенная Telegram-личность сохраняет существующий стабильный cloud user ID (включая текущие `tg:...`) на всех устройствах; контракт anchors не меняет user IDs или membership. Точные таблицы, owner sentinels, add/update allowlists, разрешения автора и read-state, совместимость старых клиентов и protected rollout — COMM-03, с отдельным явным разрешением на live schema/ACL.

Устойчивые ID обеспечивают идемпотентность отправки/повтора; повтор загрузки не создаёт второе сообщение. Локальная запись, облачная синхронизация, готовность файла и прочтение — разные состояния. Async-владелец отвечает за отмену/устаревший результат, повтор, object URL и cleanup; ошибка медиа не блокирует shell или текстовую историю. Комментарий никогда не изменяет PLAN/FACT и не сохраняет второй mutable-снимок тренировки.

**Одобрено владельцем при COMM-03:** сообщения/read-state/вложения используют обычный `owner`.
Участник без соответствующих общих update/manage grants не может править чужие строки.
Владелец строки имеет полные права на неё; сохранение автора/thread/realm в обычных
операциях обеспечивает доменный репозиторий, не отдельная строгая серверная гарантия.
Новые сервисы, realm на каждое сообщение/автора и grant-деревья не вводятся.
Для фото, видео и голосовых обе роли получают `add: messageAttachments`; собственные
метаданные автор обновляет/удаляет как owner, общих update/manage для вложений нет.
`uploadState` отражает ход загрузки, а `confirmedAt` — результат штатного confirm.
Они не являются серверным доказательством существования объекта: будущий шлюз
независимо проверяет identity/realm/message, фактический объект и его метаданные.
Повтор использует прежние messageId/attachmentId и storageKey, без второй реплики.
Подробный scope protected operator и безопасное включение v15 —
[discussion-schema-acl-plan.md](discussion-schema-acl-plan.md).

## 7. Старые comment/notes: классификация до изменения

Интеграция меню программы/плановой тренировки и инвентарь её PLAN-полей:
[COMM-06 — точки входа](discussion-entity-entry-points.md). COMM-06 регистрирует v15/v16/v17 в обычном account lifecycle без feature flag или ручного включения. COMM-07 переиспользует этот путь; новых механизмов активации нет. Real-account ACL/device acceptance остаётся отдельной проверкой.
Подробности execution: [COMM-07 — фактические сущности](discussion-execution-entry-points.md). Общий список и навигация: [COMM-08](discussion-inbox.md).

Встроенные коммуникационные `comment`/`notes` **упраздняются из UX**, оставляется вход через меню. Это не разрешение удалить одноимённые бизнес-поля. Инвентарь COMM-06/07 сохраняется в документах точек входа: таблица/поле, текущие UI/read/write/copy потребители, смысл, visibility и способ сохранения данных.

| Категория | Обращение |
| --- | --- |
| Предписание/инструкция PLAN | Сохранить бизнес-смысл и данные; менять PLAN только после отдельного подтверждения |
| Личная рабочая заметка | Сохранить приватность; не переносить автоматически в shared thread |
| Коммуникационное сообщение | Убрать второй редактор из UX; подготовить явный путь сохранения/переноса истории с provenance и доступом |
| Неоднозначное legacy-поле | Не удалять и не переименовывать вслепую; показать владельцу конкретный случай |

В runtime уже есть `comment` в occurrence PLAN и session/set, `notes` в exercise. Тесты `workout-occurrence-edit.test.ts`, `workout-copy.test.ts`, `SessionExercise.program.test.tsx` проверяют в том числе сохранение предписаний и разделение PLAN/FACT. Они остаются действующими: новый коммуникационный контракт не отменяет эти бизнес-инварианты. Этот PR не меняет тесты и не мигрирует пользовательские данные. Нельзя трактовать все поля по имени как переписку, стирать их или автоматически раскрывать тренеру.

## 8. Медиа и доступность без VPN

MVP: текст, **голосовые, записанные внутри Mezfit**, фото и видео **из галереи**. Видео — до **3 минут**, **без автоматического сжатия до измерений**. Разрешено вложение без текста. Кружки и звонки вне MVP. Поддержку MediaRecorder/кодеков, duration validation и воспроизведение проверить на настоящих Android/iOS WebView; не обещать нативный Telegram-формат записи. Нет разрешения молча перекодировать видео или снизить лимит из-за технических ограничений.

**Исключение COMM-09 для тестового MVP, утверждено владельцем 2026-11-09.**
Приложение загружает несекретные тестовые файлы анонимным PUT в выделенный
префикс `mvp-media/` Yandex Object Storage. Постоянный URL со случайным
256-битным ключом доступен любому, кто знает ссылку. Публичный листинг,
удаление, изменение ACL и доступ к приватным префиксам не разрешаются.
Авторизация медиа возвращается в отдельной задаче. Dexie хранит бизнес-данные
и не участвует в передаче файла. Подключение ссылок к сообщениям выполняется
отдельно. Client direct R2/Cloudflare Worker для медиа запрещены.
Настройка и приёмка описаны в [инструкции](../operations/communications/yandex-direct-media-mvp.md).

**Фоновая загрузка запрошена**, но непрерывная работа после сворачивания Telegram/блокировки iOS не считается доказанной. Media-адаптер отвечает за очередь, восстановление после resume/обрыва, идемпотентное подтверждение и очистку незавершённых файлов. Полное офлайн-хранение гигабайт в WebView не обещается. Если WebView не поддерживает требуемое поведение, представить измерения и запросить решение владельца; не подменять требование фоновой загрузки молча.

## 9. Telegram-уведомления

На **каждое новое сообщение** — отдельное уведомление через Telegram Bot адресату. Никакой агрегации, напоминаний, quiet-hours-логики или эскалаций в этом контракте. Идемпотентный идентификатор события предотвращает дубли при повторах доставки, не объединяя разные сообщения. Триггер и обработка незавершённого вложения уточняются как технический протокол в COMM-09/12: не выдавать неготовый файл за доставленный и не терять событие сообщения.

Бот **только открывает Mezfit** по адресному deep link (§5); ответы, копии переписки и двусторонний Telegram bridge не входят в MVP. Недоступность Telegram push без VPN не блокирует чтение/ответ в уже работающем Mezfit. «Bot API принял» не означает «push показан» или «прочитано». Каноническая история и непрочитанные — в Dexie, а не в состоянии бота. Бот-токен остаётся на сервере.

## 10. Хранение, завершение отношений и удаление

**Медиа хранятся 6 календарных месяцев после окончания отношений**, не 180 дней и не от даты загрузки. COMM-13 фиксирует авторитетный момент окончания, календарное вычисление срока и идемпотентную очистку с проверками границы месяца. Удаление сообщения и его медиа обрабатывается согласованно, включая цитаты, orphan upload и доступные подписи; это не бизнес-статус ветки.

**Текстовую историю не удалять автоматически без отдельной политики. Бывший тренер и клиент продолжают читать свою прежнюю совместную переписку и вложения, пока соответствующие материалы хранятся в системе.** Это утверждённое уточнение MVP от 2026-11-06 в [issue #638](https://github.com/buropotok/mezfit/issues/638): завершение отношений само по себе не отзывает исторический доступ. Медиа по-прежнему удаляются через 6 календарных месяцев после окончания отношений (COMM-13). История личной области и другой пары не раскрывается; новый тренер не получает старую историю по факту подключения или доступа к исторической программе.

Фактическая модель связи сейчас — канонический shared realm и две принятые membership (`shared/approved-relationship.ts`, `worker/lib/dexie-cloud-membership.ts`). В проверенных runtime-путях не обнаружена операция завершения связи с удалением membership; наличие будущего lifecycle окончания этим не доказывается. Удаление membership, если его добавить, лишит участника cloud-видимости даже его собственных записей. Поэтому будущая операция окончания сотрудничества должна сохранять историческую видимость этой пары и отдельно учитывать точный текущий контракт membership. Production membership/ACL в COMM-03 без отдельного разрешения не менять. Подробности и ограничение штатных ACL — в [discussion-schema-acl-plan.md](discussion-schema-acl-plan.md).

## 13. Приёмка на устройствах

CI не доказывает работу Mini App без VPN. Итоговая приёмка — реальные Android/iOS внутри Telegram, реальные роли и несколько устройств. Без результатов сценарий остаётся непроверенным.

1. Открыть Mini App при VPN → выключить VPN → прочитать, отправить текст/вложение, получить ответ и синхронизировать. Отдельно cold start и истечение/обновление токенов без VPN, а не только тёплая сессия.
2. Клиент: конкретный выполненный подход → меню → ветка → тестовое видео + текст либо вложение без текста. Тренер: уведомление → точный подход → открытый sheet → точное сообщение → reply голосом/текстом. Закрыть sheet, остаться на подходе; открыть ту же историю из ленты и вкладки клиента.
3. Planned → Start → completed сохраняют одну ветку и parent path; одинаковые упражнения, перестановки, копии и удалённый объект не перенаправляют историю. У шаблона программы доступны только ветки программы целиком.
4. Проверить чужие anchor/thread/message/media key, два тренера, историческую личную программу, приватные заметки и запрет расширения доступа при новом подключении.
5. Офлайн текст/правка/удаление → resume/синхронизация без дублей; unread независим у участников и согласован на устройствах одного пользователя; reply/jump после edit/delete честен.
6. Реальная загрузка без VPN, CORS/Range/подпись/expiry, лимит 3 минуты, отсутствие автосжатия, сворачивание/обрыв/повтор и отсутствие ложной готовности файла. Использовать несекретные тестовые медиа, ручные результаты не содержат приватных файлов/ключей.
7. Проверить границы retention и отсутствие автоматического удаления текстов; объёмы/расходы записать по измерениям, нерешённые блокеры не отмечать готовыми.
