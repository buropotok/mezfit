# Mezfit communications — рабочая коммуникация через Telegram

**Статус:** согласованное продуктовое направление; технический контракт и UX-детали требуют прототипа.  
**Дата:** 2026-10-18.  
**Область:** Coach / Client, тренировки и их обратная связь, Telegram Bot, локальное хранение и Dexie Cloud.  
**Связанные документы:** [AGENTS.md](../../AGENTS.md), [local-first-storage-sync.md](local-first-storage-sync.md), [product invariants](../product/invariants.md).

## 1. Назначение и граница продукта

Mezfit — приложение для PLAN/FACT, просмотра техники и **первичного разбора тренировки**. Telegram — нативная среда для **дальнейшего рабочего общения**, медиаархива и уведомлений. В Mezfit **не создаём мессенджер**: отсутствуют диалоги, лента переписки, произвольные ответы на сообщения и самостоятельная доставка чата.

Пользователи имеют два пространства общения:

- **Личный чат тренера и клиента:** встречи, организационные вопросы, свободная переписка. Mezfit его не читает и не структурирует.
- **Общий Mezfit Bot, но у каждого пользователя свой личный чат с ботом:** отчёты о тренировках, вопросы по упражнениям, ответные голосовые/кружки, статусы и напоминания. Бот явно показывает реального автора сообщения.

Telegram Bot — **коммуникационный посредник**, не AI-собеседник. Разговор идёт между людьми: в тексте указан автор; в голосовых и видео узнаваемы голос и лицо автора.

## 2. Единица организации — связь тренер–клиент

Одна действующая связь `coachClientId` соответствует **двум Telegram Topics** в частных чатах с тем же ботом:

| Участник | Тема в его чате с ботом | Содержимое |
| --- | --- | --- |
| Тренер | Имя клиента | Отчёты, ответы, вопросы и состояние работы с клиентом |
| Клиент | Имя тренера | Отчёты этого тренера, вопросы, ответы |

Темы создаются ботом по мере подключения пользователя / начала рабочей коммуникации, а не для каждого подхода или тренировки. Стабильный `coachClientId` — доменная идентичность, `chat_id` и `message_thread_id` — изменяемые внешние адреса. Клиент может иметь нескольких тренеров; данные и маршруты каждой пары изолированы.

Если тема удалена, недоступна или Telegram возвращает ошибку маршрутизации, бизнес-связь не исчезает: интеграция восстанавливает тему либо доставляет безопасным запасным способом в личный чат бота с явным контекстом и уведомляет о проблеме. Нельзя направлять сообщения в случайную тему.

**Отдельные темы на каждую тренировку и упражнение не создаём.** Одна тренировка — один опубликованный Rich Message / отчёт; внутри него разделы по упражнениям и подходам.

## 3. Сквозной пользовательский сценарий

### 3.1. Клиент завершает тренировку

1. Клиент заполняет FACT, при необходимости записывает голосовое или видео техники **у конкретного подхода** в Mezfit.
2. Файлы и метаданные сохраняются локально. Затем синхронизируются с Dexie Cloud; отсутствие VPN не является самостоятельным индикатором отсутствия сети.
3. Клиент явно завершает тренировку. После серверного подтверждения состояния бот уведомляет тренера: кто завершил, дата, день программы, есть ли медиа, deep link к тренировке.
4. Создаётся задача проверки, но только один раз на завершение конкретной сессии.

### 3.2. Первичный разбор тренером — только в Mezfit

1. Тренер открывает тренировку по ссылке из уведомления.
2. Проверяет FACT, веса, повторы и прикреплённые клиентом медиа.
3. Добавляет первичные замечания к тренировке, упражнению или подходу: текст, голос или видео. До публикации это редактируемый материал разбора, а не переписка.
4. Если замечаний нет, предусмотрено явное действие «Проверено, замечаний нет»; не заставляем генерировать замечания ради закрытия задачи.
5. Тренер нажимает **«Отправить обратную связь»**. Это **единственный продуктовый триггер публикации разбора**. Простое сохранение/синхронизация черновиков не отправляет клиенту отчёт.

Запрос публикации фиксирует **неизменяемую версию/snapshot** отчёта. Если локальные медиа не загружены, публикация находится в ожидании загрузки; пользователю не показывается ложный статус «доставлено».

### 3.3. Один отчёт — две адресные копии Telegram

После готовности snapshot и медиа Worker публикует Rich Message в:

- тему клиента у тренера — архив и опорное сообщение для ответов тренера;
- тему тренера у клиента — отчёт для просмотра и дальнейшего обсуждения.

Две Telegram-копии принадлежат **одной версии отчёта** Mezfit, но имеют разные адреса `(chat_id, message_thread_id, message_id)`. Успех одной отправки не означает успех другой; очередь повторяет только недоставленную сторону. Telegram подтверждает приём отправленного ботом сообщения, но **не прочтение пользователем и не показ push на устройстве**.

**Ручная пересылка тренером больше не нужна.** Бот вправе отправлять каждому участнику напрямую после того, как тот активировал диалог/разрешил связь с ботом; получение доступа к личным пользовательским перепискам не требуется.

### 3.4. После публикации общение остаётся в Telegram

Клиент читает отчёт и нажимает **«Ответить»** под нужным упражнением или подходом. Бот создаёт короткое адресное приглашение к ответу (например, через `ForceReply`), привязанное к исходному `workoutSessionId` и, если возможно, `sessionExerciseId` / `sessionSetId`. Клиент отправляет текст, голосовое или кружок штатной записью Telegram.

Бот определяет контекст по собственному `(chat_id, prompt_message_id)` и направляет ответ в тему этого клиента у тренера. Тренер нажимает «Ответить» на поступившее сообщение; его ответ маршрутизируется обратно клиенту с тем же контекстом. Любое новое ответное сообщение получает собственную кнопку «Ответить».

**Обычный Reply на весь отчёт** относится к тренировке в целом. **Произвольное сообщение боту без связанного контекста** не должно автоматически приписываться последнему упражнению. Предлагается предложить выбор контекста либо пометить его как общий вопрос в рамках пары.

Несколько одновременно открытых приглашений к ответу допустимы: контекст привязывается к ID конкретного приглашения, а не к глобальной переменной «последнее упражнение». Если пользователь отвечает на устаревшее/неизвестное приглашение, бот просит заново выбрать контекст.

**После публикации не продолжаем переписку в Mezfit.** Отчёт можно просматривать из тренировки. Новые существенные изменения разбора создают отдельную версию/дополнение, а не молча переписывают историческое Telegram-сообщение.

## 4. Rich Message — формат отчёта

Отчёт содержит:

- дату и время тренировки, день/название программы, реального автора разбора;
- разделы по упражнениям, а при необходимости — по подходам, с фактическими данными;
- видимые краткие замечания тренера;
- сворачиваемые блоки (Details) с фото, GIF-анимацией техники, голосовыми и видео, если клиентам это удобно на практике;
- **крупную «Ответить» под каждым адресуемым разделом**;
- кнопку/ссылку **«Открыть в Mezfit»** с deep link на тренировку;
- уникальный поисковый хэштег тренировки, например `#mz_w_7K2PR8Q`; для отдельных комментариев допускаются дополнительные уникальные хэштеги.

Внешний вид нативных Telegram-блоков и кнопок определяет Telegram, а не UIkit Mezfit. Используем изображения/анимации из разрешённого каталога Mezfit; не дублируем тяжёлые GIF без необходимости.

Кнопки в Rich Message и вызовы `callback_query` создают контекст обращения. Сами параметры кнопок не являются авторизацией: сервер сверяет Telegram-аккаунт, связь, роль, тренировку и право участия. Если отчёт превышает поддерживаемые лимиты блоков/медиа, его нужно безопасно разбить на несколько связанных сообщений с отдельными контекстными действиями, а не молча урезать или считать отправленным частично.

## 5. Контроль исполнения — конечные автоматы

**Проверка тренировки** (на каждую завершённую сессию):

`awaiting_review` → `review_in_progress` → (`reviewed_no_changes` **или** `feedback_draft`) → `publication_requested`.

**Публикация версии отчёта** (на конкретный snapshot, отдельно от проверки):

`pending_media` → `ready_to_send` → `sending` → `sent_to_client_and_coach`.

Неуспешные отправки и частичная доставка — явные состояния/сведения по каждому получателю, с повторной обработкой и сообщением об ошибке. Публикация не отмечается завершённой, пока не подтверждены обе нужные Telegram-копии или не зафиксирован явный продуктовый обход.

**Разговоры после отчёта** — не продолжение линейного автомата публикации. Это несколько параллельных цепочек ответов, каждая связана с отчётом и упражнением / подходом.

**Клиентское «Подтвердить получение»** может служить отдельным необязательным событием `acknowledged_at`. Его отсутствие не отменяет подтверждённой Telegram API отправки и не является доказательством непрочитанного сообщения.

### Уведомления и напоминания

- Завершение тренировки → тренеру поступает задача на проверку.
- Истёк согласованный срок без проверки → агрегированное напоминание тренеру.
- Ошибка/задержка публикации → технический статус и контролируемые повторы; не спамить медиа.
- Отчёт доставлен → Telegram-уведомление клиенту и архивная копия тренеру.
- Новый вопрос → уведомление адресату в соответствующей теме; повторные напоминания по всем репликам **не создаются автоматически**.

Правила SLA, расписание напоминаний, quiet hours и политики эскалации **не утверждены**; это будущая продуктовая настройка. Система контролирует незавершённую профессиональную обратную связь, а не каждую реплику.

## 6. Источники данных и интеграционные границы

Соблюдаем [local-first контракт](local-first-storage-sync.md):

- **Dexie / IndexedDB:** локальная работа с FACT, черновиком разбора и медиа до синхронизации.
- **Dexie Cloud:** единственная авторитетная бизнес-БД (тренировки, отчёты, версии, задачи обратной связи, состояние доставки и разрешённые метаданные маршрутизации). Клиентские FACT/медиа и опубликованные для обоих участников данные принадлежат shared realm конкретной пары. **Неопубликованный черновик тренера не должен быть доступен клиенту:** хранить его в coach-private realm либо применять явно проверенные серверные права чтения/записи; перенос/публикация разрешённого snapshot выполняется через надлежащую доменную операцию. Одной UI-невидимости недостаточно.
- **Медиахранилище:** Dexie Cloud Blob Offloading при подтверждённой совместимости/правах серверного чтения либо отдельное защищённое R2-хранилище по явному архитектурному решению. Хранение файла локально не означает его доступность боту.
- **Cloudflare Worker:** доверенная проверка Telegram webhook/update и Dexie Cloud webhook, авторизация, маршрутизация, формирование Telegram Rich Message, постановка внешних отправок в очередь. Worker не является вторым сервисом бизнес-CRUD и не создаёт свой движок синхронизации.
- **Telegram:** транспорт, интерфейс ответов, push, долговременная доступная пользователю история медиа. Telegram-копия **не заменяет** облачное хранение Mezfit и не гарантирует вечную сохранность.

Имена сущностей для проектирования (не готовая схема/таблицы): `WorkoutFeedbackTask`, `FeedbackDraft`, `PublishedFeedbackReport`, `TelegramTopicBinding`, `TelegramMessageBinding`, `ContextReplyPrompt` и события доставки. Стабильные строковые ID генерируются в Mezfit; таблицы/контракты проектируются в отдельном implementation PR.

Ключи маршрутизации: `coachClientId`, `workoutSessionId`, опциональные `sessionExerciseId`/`sessionSetId`, версия отчёта, `chat_id` + `message_id`; при наличии темы — `message_thread_id`. Нельзя использовать один `message_id` без `chat_id`.

### Асинхронность и надёжность

Dexie Cloud Web Hooks могут сообщать о синхронизированных изменениях, но не гарантируют один webhook на каждую мутацию. Worker валидирует подпись/секрет webhook, заново проверяет актуальное серверное состояние и готовность всех медиа, а не доверяет одному входящему событию.

Отправки на Telegram — через контролируемую очередь с повторными попытками, rate limits, идемпотентной бизнес-обработкой по `reportVersionId + recipientId` и журналом подтверждённых результатов. **Абсолютной exactly-once доставки Bot API не обещаем:** если сеть оборвалась после фактической отправки и до сохранения результата, возможен дубль; нужны стратегия восстановления/сверки и видимый статус.

Если пользователь заблокировал бота, не активировал диалог, удалил тему или у него отсутствует доступ к отчёту, это отдельная ошибка/состояние. Нельзя переносить чужой контент в другой realm/чат только для «успешной доставки».

## 7. Безопасность, приватность, доступ

1. Бот получает сообщения только своих диалогов с пользователями и необходимые callback-события. Личный чат тренера с клиентом вне Mezfit не читается.
2. Входящие Telegram-события привязываются к проверенному `from.id`, а не к переданным пользователем `coachClientId` или `workoutSessionId`.
3. На каждую маршрутизацию проверяются действующая связь тренер–клиент, разрешённое направление сообщения и доступ к конкретному упражнению/тренировке.
4. Deep link открывает нужный экран только после авторизации, не предоставляет доступ по одному идентификатору.
5. Медиа доступны бот-интеграции только через проверенный серверный доступ с минимальными правами. Никаких bot tokens / глобальных Dexie Cloud ключей на клиенте и никаких постоянных публичных ссылок на личные видео.
6. Следует объяснить пользователям, что рабочие сообщения проходят через сервер Mezfit и бот. Политики удаления, хранения и отзыва доступа определяются отдельно.
7. При завершении отношений тренер–клиент новые маршруты запрещаются; дальнейшая доступность уже существующей истории в Telegram и архивов Mezfit требует отдельной политики.

## 8. Что не входит в выбранную концепцию

- Пересылка тренером готовых отчётов вручную и кнопка «Я переслал» (заменено прямой отправкой ботом).
- Группы с отдельными клиентами или Telegram Topics на каждую тренировку/упражнение.
- Мессенджер, список диалогов и двухсторонняя переписка внутри Mezfit.
- Автоматический анализ вопросов AI, преобразование свободного текста в упражнение, чтение личной переписки через Business API.
- Гарантированный push без VPN на всех устройствах: в обсуждении доставка была **проверена пользователем на Android и iOS** в его условиях, но общая гарантия платформы не вытекает из одного теста.

## 9. Что подтверждено документацией, а что ещё проверить

**Официально описаны:**

- [Telegram Bot API — private topics / `createForumTopic`](https://core.telegram.org/bots/api#createforumtopic) и `message_thread_id` для доставки;
- [Telegram Bot API — Rich Messages / `sendRichMessage`](https://core.telegram.org/bots/api#sendrichmessage): медиа, сворачиваемые блоки, кнопки, deep links;
- [Telegram Bot API — `ForceReply`](https://core.telegram.org/bots/api#forcereply);
- [Dexie Cloud — Blob Offloading](https://dexie.org/docs/cloud/blob-offloading) и [Web Hooks](https://dexie.org/docs/cloud/web-hooks).

**Критические проверки до реализации:**

1. Тестовый Rich Message: несколько упражнений, `Details`, GIF/видео/голосовое, встроенные кнопки после упражнения — iOS и Android.
2. Нажатие «Ответить» → `callback_query` → `ForceReply` → запись **голосового и кружка** с сохранением конкретного Reply-контекста; несколько параллельных вопросов.
3. Создание/пересоздание частной темы, отправка в `message_thread_id` и fallback при ошибке темы; при двух тренерах у одного клиента — полная изоляция.
4. Локальная запись медиа в Telegram WebView, квоты устройства, безопасное поведение при закрытии Mini App и загрузке после возобновления.
5. Dexie Cloud Server Blob Offloading и безопасное серверное чтение медиа по realm; лимиты/форматы Telegram Rich Message и максимальные размеры файлов.
6. Реальная пара пользователей: завершение → уведомление → первичный разбор → публикация обоим → контекстный голосовой вопрос → ответ тренера.
7. Серверные права, сбои/частичная доставка, дубли после повтора webhook и поведение при блокировке бота.

## 10. Условия приёмки будущей реализации

- Пользователь не выбирает адресата и не вводит ID или хэштег вручную для рабочего ответа.
- Тренер может разобрать уже синхронизированную тренировку локально и запросить публикацию; отчёт не уходит клиенту до явного действия «Отправить обратную связь».
- Обе адресные копии отчёта появляются в соответствующих темах, а точный статус каждой подтверждён сервером.
- Из сообщения по упражнению отправляется адресный текстовый/голосовой/видеоответ; другая сторона может продолжить тот же контекст кнопкой «Ответить».
- Связи чужого клиента, тренировки, упражнения или подхода невозможно получить подбором ID/`callback_data`.
- Тренер получает напоминания о непроверенных завершённых тренировках, но не получает лавину напоминаний по каждой реплике.
- Для пользователя свободный личный чат остаётся отдельным от структурированной рабочей коммуникации с Mezfit Bot.

**Решение:** принять этот документ как продуктово-архитектурный ориентир; схемы таблиц, API, фоновые задания, частные UX-поведения и порядок PR закреплять отдельно после перечисленных проверок.
