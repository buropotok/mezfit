# Mezfit communications — контекстные обсуждения

**Статус:** согласованное продуктовое направление; архитектурная спецификация для будущей реализации, не описание действующего функционала.  
**Дата решения:** 2026-11-05.  
**Область:** Coach / Client, программы, тренировки, упражнения, подходы, сообщения, медиа и уведомления.  
**Заменяет:** прежнюю продуктовую концепцию коммуникации преимущественно через Telegram от 2026-10-18.  
**Связанные документы:** [AGENTS.md](../../AGENTS.md), [local-first-storage-sync.md](local-first-storage-sync.md), [product invariants](../product/invariants.md), [typography.md](../../typography.md).

## 1. Продуктовый принцип

Mezfit строит **единую систему контекстных обсуждений**, а не обычный бесконечный чат тренера с клиентом.

Обсуждение привязано к конкретному внутреннему объекту Mezfit: программе, тренировке, упражнению или подходу. Сообщения и вложения существуют в одной канонической ветке; интерфейс самой сущности и общий **Центр обсуждений** лишь показывают разные проекции той же ветки.

Непременные правила:

1. Любая кнопка «Комментарий» / «Обсуждение» знает объект, из которого вызвана; пользователь не вводит ID и не выбирает контекст повторно.
2. Каждая ветка доступна **из своей сущности** и из **Центра обсуждений**. Из ветки есть обратный переход к точному объекту, а не просто к экрану верхнего уровня.
3. Список обсуждений состоит из **веток по конкретным вопросам**, а не из отдельных сообщений в одном бесконечном диалоге.
4. У одного объекта может быть несколько независимых веток. Внутри одной ветки — линейная переписка без древовидных ответов на ответы в MVP.
5. Канонические данные сообщений принадлежат Mezfit. Telegram не является обязательным транспортом, историей или медиахранилищем.
6. Поведение домена одинаково для Telegram Mini App и будущих нативных оболочек iOS/Android на Capacitor.

Свободная личная переписка вне Mezfit остаётся внешней по отношению к продукту: приложение не читает личные сообщения Telegram. В MVP не вводим второй универсальный «чат обо всём», который конкурирует с контекстными ветками.

## 2. Объекты обсуждения и идентичность

Привязка состоит как минимум из типа объекта, его **стабильного идентификатора**, отношения Coach–Client и realm. Типы нельзя определять по названию упражнения, порядковому номеру или отображаемому тексту.

| Продуктовый уровень | Примеры реальных доменных объектов | Принцип |
| --- | --- | --- |
| Программа | training plan, его элементы PLAN | Обсуждение назначения/структуры программы |
| Тренировка | календарная workout occurrence или выполненная session | Контекст конкретной тренировки, а не всех тренировок одного дня программы |
| Упражнение | упражнение в программе, occurrence snapshot или выполненной session | Разные экземпляры одного упражнения не сливаются |
| Подход | program set, occurrence-plan set или execution/FACT set | Комментарий к фактически выполненному подходу не превращается в комментарий к шаблону |

В действующем коде присутствуют, в частности, **CloudTrainingPlanRow**, **CloudProgramExerciseRow**, **CloudProgramSetRow**, **CloudWorkoutOccurrenceRow** и **AdHocSessionRow / AdHocExerciseRow / AdHocSetRow**; сохранённый occurrence PLAN также содержит собственные ID вложенных упражнений и подходов. Существуют отдельные legacy/session FACT-модели. Реализация обязана явно сопоставить каждый видимый экран с его истинным доменным типом и идентификатором, не подменяя их source ID и не опираясь на позицию в списке.

Ветка содержит:

- точный **anchor**: тип сущности + ID (+ ID родителя, если для вложенного snapshot требуется составная идентификация);
- **context path**: типизированные ID предков, например программа → тренировка → упражнение → подход, исключительно для навигации/агрегации;
- **title/context snapshot**: исторические отображаемые название, дата, упражнение, номер подхода, вес и повторы при создании ветки;
- отдельные **realmId** и идентификатор отношения **coachClientId**.

Context path не даёт права доступа и не является вторым источником истины для PLAN/FACT. Исторический snapshot не заменяет текущую доменную запись; используются ID и реальные связи. Смена порядка, переименование и архивирование объекта не должны перепривязывать обсуждение к другому объекту.

Для персональных сущностей без Coach–Client отношения модель должна явно различать личную область и совместное обсуждение. Нельзя автоматически публиковать персональные данные тренеру только потому, что позже появилась связь. Правила создания личных обсуждений и их последующего распространения — отдельное продуктовое решение.

## 3. Ветки, сообщения и статусы

**DiscussionThread** — независимый вопрос или тема внутри объекта. Например, у третьего подхода могут существовать две ветки: «Глубина приседа» и «Боль в колене». Нажатие на кнопку объекта показывает его ветки, позволяет открыть существующую или создать новую. Если ветка одна, допустим быстрый переход непосредственно к ней.

**DiscussionMessage** — конкретная реплика в ветке с автором, временем, текстом и возможными вложениями. Реплики имеют стабильные ID и не дублируются в родителе, списке клиентов или Telegram. Ответ в ветке сохраняет тот же anchor через ссылку на threadId, даже если пользователь пришёл из Центра обсуждений.

**MessageAttachment** — отдельный объект медиа, связанный с сообщением: изображение, видео, голосовое, видеокружок либо другое поддерживаемое вложение. В сообщении может быть текст вместе с видео. Нативный формат «голосовое» или «кружок» определяется возможностями устройства и кодека; в браузере нельзя обещать идентичный Telegram-формат без проверки или конвертации.

Минимальные продуктовые статусы ветки: **открыта** и **решена**. «Прочитано», «ожидает ответа» и «решена» — разные измерения. Прочтение хранится **отдельно для каждого участника**, а статус решения относится к ветке. «Требует ответа» необходимо вычислять по роли/последнему значимому действию или по явному признаку назначения; его нельзя слепо приравнивать к непрочитанному.

Физическое удаление доменного объекта не должно терять историю общения. При логическом удалении/архивировании ссылка сохраняет доступную историю и, если прямой переход недоступен, показывает честную метку «объект недоступен» с историческим контекстом. Запрещено молча направлять в другой подход.

## 4. Сквозной сценарий: видео третьего подхода

1. Клиент выполняет подход и записывает видео обычной камерой телефона.
2. В Mezfit открывает **конкретную выполненную тренировку → упражнение → подход**, нажимает «Обсуждение», создаёт ветку или выбирает нужную.
3. Пишет, например, «Посмотри глубину приседа» и выбирает видео из галереи. Контекст подхода устанавливается автоматически.
4. Текст и метаданные локально фиксируются через типизированный репозиторий; загрузка файла выполняется независимо. Клиент видит честный локальный/сетевой статус и может повторить неудачную загрузку, не создавая вторую реплику.
5. После готовности сообщения и медиа тренер получает событие в Центре обсуждений, а при доступном канале — push со ссылкой на **эту** ветку и **этот** подход.
6. Тренер открывает ссылку, попадает в нужный контекст тренировки, видит видео и комментарий, отвечает текстом/голосом/видео.
7. Клиент видит ответ в том же обсуждении, а позднее может из истории подхода восстановить и видео, и весь диалог.

Не считать файл доставленным по одному факту локального сохранения или запуска отправки. Сообщение не должно ложно показывать вложение как доступное до подтверждения его загрузки. Политика видимости незавершённого сообщения у адресата определяется отдельно, но если промежуточное состояние синхронизировалось, интерфейс обязан показывать его корректно.

## 5. Отображение внутри сущностей

Ни программа, ни карточка упражнения, ни подход **не превращаются в длинную переписку**. Около кнопки показывается компактный агрегат: число веток, число непрочитанных, миниатюра вложения и/или краткая последняя реплика, если это уместно для данного экрана.

- **Подход:** только ветки этого конкретного экземпляра подхода; прикреплённые видео и ответы. Никаких обсуждений одноимённого подхода в других тренировках.
- **Упражнение:** собственные ветки упражнения и сгруппированные ветки вложенных подходов.
- **Тренировка:** собственные ветки плюс сгруппированные обсуждения упражнений и подходов этой тренировки.
- **Программа:** собственные ветки плюс относящиеся к её PLAN-структуре ветки. Исторические выполненные тренировки не смешиваются с шаблоном автоматически; их можно показывать через отдельную явную проекцию.

Агрегация идёт через реальные родительские ID и заранее определённые проекции, без дублирования реплик. Количество «веток» и количество «непрочитанных сообщений» не взаимозаменяемы; счётчики и подсказки должны это отражать.

Кнопка из любой сущности открывает соответствующий список веток/конкретную ветку. Создание новой ветки — явное действие с темой/первой репликой. Не следует плодить отдельную ветку на каждое последующее сообщение.

## 6. Центр обсуждений

Единый раздел **«Обсуждения»** доступен обеим ролям, но показывает только отношения и контент, на которые у пользователя есть подтверждённые права.

Основной элемент списка — **ветка** с именем собеседника, структурированным путём к объекту, кратким превью последней реплики, датой активности, состоянием, числом непрочитанных и при необходимости признаком медиа. Сортировка по последней активности ветки.

Необходимые проекции и фильтры:

- все ветки / непрочитанные / требующие ответа / решённые;
- выбор клиента или тренера, программы, тренировки и уровня объекта;
- группировка по Coach–Client отношению и по иерархии сущностей, когда пользователь хочет изучить историю;
- адресный поиск по доступным текстам и контекстам без раскрытия чужих данных.

В открытой ветке всегда виден компактный **контекстный заголовок/хлебные крошки**, который ведёт к исходному объекту. Из объекта по кнопке обсуждений можно вернуться в эту же ветку. Навигация должна восстанавливать точные occurrence/session/exercise/set, состояние экрана и корректную историю Back.

Уведомление о сообщении открывает адресную ветку. При необходимости можно сначала показать сам подход с открытым обсуждением; это единая навигационная операция, а не два конкурирующих маршрута. Если объект недоступен, объяснить причину без утечки сведений.

## 7. UI: штатные Konsta Messages 5.4.0

Визуальная основа будущего экрана — закреплённая в Mezfit **Konsta UI 5.4.0**, тема **iOS + dark**:

| Публичный примитив | Роль в Mezfit |
| --- | --- |
| Messages | Лента одной открытой ветки |
| Message | Входящие/исходящие сообщения, имя, аватар, метаданные |
| MessagesTitle | Даты и групповые разделители |
| Messagebar | Панель текста с левым/правым слотами действий |

Использовать публичные свойства, слоты и стандартную механику Konsta, без изменения установленных файлов библиотеки и без CSS-override внутренних классов из продуктовых экранов. Свойство **Message.text** принимает React-контент: там можно размещать прикладной плеер, изображение, карточку контекста или статус вложения. Загрузка медиа, запись с камеры/микрофона, кнопки отправки и ответы — логика Mezfit, не возможности самого Konsta.

Проверить ограничения текущего примитива: пузырь Message ограничен примерно **70% ширины**; у Messagebar нет гарантированного auto-grow textarea, медиа-рекордера, списка вложений и встроенного управления мобильной клавиатурой. Если для видео или ввода понадобятся иные механика/размеры, их сначала оформляют как явное расширение **src/ui/konsta-mezfit/**. При отсутствии подходящего публичного/адаптерного API сообщают о нехватке возможности UIkit, не маскируют её локальными селекторами. Типографика прикладного контента — только семантические пресеты из typography.md; нативная типографика Konsta не переопределяется.

Первая реализация может ограничиться текстовыми репликами; визуальное добавление аудио/видео не должно требовать перестройки модели ветки.

## 8. Данные и local-first контракт

Предлагаемая **концептуальная** модель, не утверждённая миграция или готовый Dexie schema contract:

| Сущность | Существенные поля |
| --- | --- |
| DiscussionThread | id, realmId, coachClientId, anchorType, anchorId, parent/context IDs, titleSnapshot, status, createdAt, updatedAt, lastActivityAt |
| DiscussionMessage | id, realmId, threadId, authorUserId, text, createdAt, clientGeneratedId |
| MessageAttachment | id, realmId, messageId, mediaType, storageKey, sizeBytes, mimeType, duration, upload state / verified metadata |
| DiscussionReadState | id, realmId, threadId, userId, lastReadMessageId/lastReadAt |

Конкретные поля и схемы уточняются перед кодом: не сохранять производные счётчики и временные подписанные URL без причины; не вводить конфликтующие mutable-дубликаты состояния. Для offline/idempotency используются устойчивые ID сообщений; повтор запроса не создаёт дубликат. Связь сообщения с веткой и ветки с исходным anchor неизменяема после создания; исправления текста, архивирование и удаление обсуждений требуют явной отдельной политики.

**Dexie Cloud — единственная авторитетная бизнес-БД:** ветки, сообщения, отношения, права, состояние обсуждения и допустимые метаданные медиа. **IndexedDB/Dexie.js** — локально доступный рабочий subset; нормальные сообщения локально коммитятся через типизированный domain repository, затем **Dexie Cloud Addon** самостоятельно синхронизирует их. React и Konsta не обращаются напрямую к Dexie или HTTP. Не создавать собственный SyncEngine, теневую бизнес-БД в Yandex или отдельные «чат-серверные» CRUD-операции.

Совместное обсуждение живёт в **shared realm конкретной связи тренер–клиент**; ни фильтр UI, ни клиентский coachClientId сами по себе не авторизуют. В каждой строке корректные realmId, owner/permissions и проверенная связь. Новые tables/grants/schema/роли требуют самостоятельного ревью и отдельного разрешённого protected rollout; существующие ACL нельзя расширять молча. Исторические личные заметки и неопубликованные тренерские черновики не должны автоматически становиться видимыми клиенту.

## 9. Медиа: Yandex Object Storage и сетевые ограничения России

**Предпочтительное целевое направление:** российский **Yandex Cloud Object Storage** для долговременных файлов — видео упражнений, фото, голосовых и кружков. Бизнес-метаданные и идентификаторы хранятся в Dexie Cloud; постоянная публичная ссылка на приватный файл не хранится.

Устройство должно загружать и воспроизводить медиа **напрямую из российского хранилища**, не прокачивая большие файлы через Dexie Cloud и не требуя доступа к Telegram или Cloudflare R2. Это решение основано на наблюдении, что Dexie Cloud работает у пользователя без VPN, тогда как Telegram и прямой Cloudflare-доступ недоступны; доступность Yandex Storage из **Mini App WebView и Capacitor** ещё следует проверить на реальных сетях.

Для приватного бакета требуется отдельный минимальный **доступный из России media authorization gateway** (например Yandex Cloud Functions): проверить установленную личность и права на конкретный realm/anchor, выдать короткоживущий scoped signed upload/read URL, проверить размер/тип/наличие файла перед подтверждением. Не выдавать S3 секреты в приложение. Не рассчитывать на запрос из устройства к Cloudflare Worker для получения подписанной ссылки: он может быть заблокирован. Gateway не становится второй авторитетной БД, должен согласованно и безопасно проверять право доступа через Dexie Cloud и не доверять только ID от клиента. Окончательный способ серверной проверки прав и доступность Dexie Cloud из gateway требуют прототипа.

Разделить жизненный цикл **текста/метаданных** и **файла**. Надёжная клиентская очередь загрузки и компенсация незавершённых вложений — зона media-адаптера; полное offline сохранение гигабайт в WebView не гарантируется. В будущем Capacitor может использовать нативные Camera/FileSystem/Media/Push адаптеры, сохраняя те же доменные контракты. При ограничениях кодека приложение либо преобразует файл явно и безопасно, либо покажет поддерживаемые варианты; не обещать нативные Telegram voice/video-note форматы в браузере без проверки.

В MVP не вводить параллельно Telegram как единственное хранилище файлов, R2 как обязательный российский путь или Dexie Cloud Blob Offloading как постоянный архив больших видео. Возможность дополнительного backend-хранилища/географического резервирования рассматривается отдельно после измерений.

## 10. Платформы, идентичность и уведомления

**Один Mezfit Core** для Telegram Mini App, будущего iOS Capacitor и Android Capacitor. Платформенные зависимости помещаются в адаптеры (auth, media capture/picker, file upload persistence, push, deep links), а не в компоненты сообщений.

Текущая аутентификация и локальные ID исходят из Telegram (в том числе существующие ID вида tg:... и конфигурация Dexie Cloud). Для будущей самостоятельной установки нужен согласованный **стабильный пользовательский идентификатор Mezfit и механизм входа/связывания аккаунтов**, который ведёт к тому же пользователю и realms из Telegram и Capacitor. Это отдельное проектирование, не разрешение менять существующие ID и membership по умолчанию.

Уведомления — производная интеграция: Telegram Bot для пользователей, которые его используют, и подходящий нативный push-канал в Capacitor после проверки доступности в РФ. Отсутствие push не блокирует синхронизацию/просмотр ветки. Из push — deep link к threadId и каноническому anchor, с проверкой роли, relationship и наличия объекта. Агрегировать частые ответы, учитывать настройки/quiet hours после отдельного продуктового решения. «Bot API принял сообщение» не означает «push показан» или «пользователь прочитал».

Telegram может дополнительно получать уведомления или копии сообщений. Возможная двухсторонняя маршрутизация ответов из бота потребует отдельного решения с безопасной привязкой к threadId, дедупликацией и сохранением канонической истории в Mezfit. Не создавать отдельные обязательные темы Telegram на каждую сущность или дублирующую чат-историю.

Нативные аудио/видеозвонки не предоставляются Konsta Messages и не решаются Bot API; для их реализации потребуется отдельный транспорт (например WebRTC) и отдельное продуктовое решение.

## 11. Надёжность, безопасность и жизненный цикл

- Все normal CRUD для сообщений — через типизированные repository/application services; поддерживать offline-first и честные статусы синхронизации. Успех локальной записи не эквивалентен облачной доставке.
- Защита доступа — на серверной стороне: realm membership, участники связи, неизменяемая identity/parent provenance, допустимые роли и доступность anchor. Запретить подбор ID, переход в чужую ветку или использование чужого media object key.
- Media gateway сверяет права **на каждый upload/read**, валидирует тип, размер, ownership и допустимые назначения, ограничивает lifetime подписи. Не хранить токены, S3 ключи или постоянные bearer-URL в Dexie.
- Обработка повторных событий, частичных ошибок и гонок: идемпотентность, отсутствие ложного статуса «доставлено», безопасное восстановление навигации, отмена устаревших async-операций и очистка незавершённых локальных ресурcов.
- Удаление/закрытие отношений, удаление сообщений, срок хранения медиа, разрешение повторного доступа к историческому архиву, правила доступа после завершения сопровождения — требуют отдельной утверждённой политики. До её принятия нельзя автоматически передавать права или удалять историю.
- При совместной работе над одной тренировкой нельзя менять PLAN или FACT ради комментария и нельзя сохранять второй mutable-снимок тренировки внутри сообщения. Указанные в context snapshot вес/повторы — только историческое описание.
- Неопубликованный черновик обратной связи тренера, если он нужен в UX, должен быть структурно приватным. Синхронизация Dexie Cloud не является публикацией: публикация всегда отдельное намерение и видимость определяется безопасной серверной моделью.

## 12. Проверки до implementation PR

1. Реальный сценарий **Coach + Client**: комментарий на выполненный подход → текст и видео → ответ → открытие из подхода и из общего Центра → обратный переход к тому же подходу.
2. Проверить ID всех разновидностей PLAN/occurrence/execution, ад-хок и legacy session; изменение позиции/названия, архивирование и удаление исходной записи не должны менять anchor.
3. Проверить real-server Dexie Cloud ACL для новых таблиц в shared realm на двух аккаунтах и попытки подобрать чужие threadId/anchorId/mediaKey.
4. Проверить Yandex Storage upload/read/signing **без VPN** в Telegram WebView (Android/iOS), Capacitor, при смене сети/возобновлении приложения, крупном файле и временном обрыве; проверить CORS, Range, ограниченные signed URLs.
5. Проверить доступность media gateway к Dexie Cloud для auth/ACL и отсутствие секретов/публичного доступа к пользовательским видео.
6. Проверить Konsta Messages/Messagebar 5.4.0 на узком экране, видео, автопрокрутке, виртуальной клавиатуре, навигации и safe areas; не модифицировать базовую механику библиотеки.
7. Проверить дедупликацию, офлайн-отправку, неуспешное медиа, повторный запуск, несуществующую ветку, статус прочтения для обоих участников и ошибки push/deep link.
8. Проверить архитектурную совместимость будущего входа из Capacitor с текущими Telegram-ориентированными ID/realm membership до запуска независимого нативного входа.

## 13. Поэтапное внедрение

1. **Контракты и идентичности:** типизированные anchor/context, правила доступности, сущности веток/сообщений/прочтения, навигационный переход без UI, schema/ACL проект и безопасный protected rollout отдельно.
2. **Текстовый вертикальный срез:** комментарий у подхода, список веток, Konsta Messages, ответ тренера, общий Центр, обратная навигация, офлайн и синхронизация Dexie Cloud. Без собственного SyncEngine.
3. **Медиа:** приватное Yandex Object Storage, gateway подписанных ссылок, загрузка из галереи, статусы, воспроизведение и обработка ошибок. Затем голосовые и видеокружки с платформенными адаптерами.
4. **Уведомления:** Telegram Bot / нативный push, авторизованные deep links, агрегирование и при необходимости дополнительный Telegram bridge.
5. **Capacitor:** самостоятельная авторизация/связывание учётных записей и нативные media/push плагины на сохранённых контрактах.

Не менять в одном PR архитектуру идентичности, облачные ACL, медиа, UI и платформенный bootstrap. Каждую часть внедрять самостоятельным согласованным вертикальным срезом; проверки кода тестов — перед PR, запуск typecheck/test/build — в CI после PR по установленному workflow.

## 14. Условия приёмки концепции

- У комментария есть ровно один точный anchor, и он никогда не перепривязывается к одноимённому или следующему подходу.
- У одной сущности допустимо несколько веток; ответы внутри ветки сохраняют общий контекст.
- Из программы/тренировки/упражнения/подхода пользователь открывает соответствующую ветку; из ветки — исходный объект.
- Родительские экраны показывают компактные агрегаты и группировки, но не бесконечные простыни; Центр обсуждений — список веток по последней активности.
- У каждого участника собственные unread-данные, отдельно от open/resolved и requires-reply; все видимые сведения ограничены полномочиями пользователя.
- Текст синхронизирует Dexie Cloud Addon; большие медиа не расходуют его бизнес-хранилище, а хранятся отдельно с проверяемыми правами.
- Telegram не обязателен для чтения, ответа и просмотра уже доступного в Mezfit файла; фактическая российская доступность Yandex будет подтверждена до реализации.
- Один набор доменных контрактов работает в Mini App и будущих Capacitor-клиентах; UI не владеет синхронизацией или API-секретами.
- Историческая связь с подходом и обсуждением сохраняется при изменении тренировочного плана и логическом удалении объекта.

**Решение:** принять описанную модель контекстных обсуждений как новое направление Mezfit. Существующая Telegram-centric концепция от 2026-10-18 этим документом **заменена** и не должна использоваться как активное техническое задание. Точные таблицы, ACL, UX-подробности, политика удаления, самостоятельная auth-модель Capacitor и сетевой прототип Yandex должны быть согласованы перед соответствующими implementation PR.
